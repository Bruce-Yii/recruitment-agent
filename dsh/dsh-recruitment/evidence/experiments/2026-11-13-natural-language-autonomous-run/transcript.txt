3: > 输入是**已经解析好的转换器输出**，输出是**行文本 + 索引 + 判定**。
4: > 这一层不调用模型、不联网、不读文件、不写文件、不取当前时间：全部是纯函数。
5: 
6: | 文件 | 作用 |
7: |---|---|
8: | `serialize.ts` | 转换器 `blocks[]` → 带 id 的行文本 + `block_index` |
9: | `validate.ts` | 模型结果 × `block_index` × 原始块文本 → `{accepted, rejected[], issues[]}` |
10: | `index.ts` | barrel（**未**接进 `src/index.ts`，见 §7） |
11: 
12: 依赖：只有 Node 内置的 `node:crypto`（算 sha256）。无第三方包。
13:

15: 
16: ## 1. 行文本契约（格式固定，不许改）
17: 
18: ```
19: #12 | p1 | 工作经历
20: #13 | p1 | 2020.07-2023.06  星河科技  后端工程师
21: ```
22: 
23: - **id 从 1 开始连续编号**，一个 block 一行；
24: - 块内换行写成 `⏎`，保证「一行一块」；
25: - 超过 `MAX_BLOCK_CHARS = 500` 字的块，按句子 / 换行边界切成多行，**每片各占一个 id**；
26: - **不丢弃任何 block**：空块也占一个 id，`block_index` 里 `empty=true`，行文本形如 `#6 | p2 | `；
27: - 拿不到页号时写 `p?`（不编造页号），`block_index.page = null`。
28: 
29: 切分规则（确定性）：
30: 
31: 1. 从限长处往回找最近的可切点；可切点 = 换行 / `。！？；…` / 后跟空白的 `. ! ? ;`；
32: 2. 片段最短 `MIN_PIECE_CHARS = 64` 字，避免切出碎句；
33: 3. 窗口内没有可切点就**硬切在 500**；
34: 4. 片段是**精确切片**：全部片段按序拼接 == 原文（不丢字、不补字、不改写）；
35: 5. 按**码点**切，emoji 等代理对不会被切成半个。
36: 
37: ## 2. `block_index`（id → page / bbox / sha256）
38: 
39: ```jsonc
40: {
41:   "version": 1,
42:   "max_block_chars": 500,
43:   "source_sha256": "<PDF 原件 sha256，取自 converter meta>",
44:   "blocks": 103,
45:   "entries": [
46:     {
47:       "id": 12, "block_no": 12,
48:       "page": 1, "bbox": [28.92, 209.95, 566.39, 226.24],
49:       "sha256": "<该行文本的 sha256>", "source_sha256": "<同上>",
50:       "chars": 32, "kind": "paragraph", "provenance": "native_text",
51:       "empty": false,
52:       "parent_id": null, "piece_index": 0, "piece_count": 1,
53:       "piece_start": 0, "piece_end": 32
54:     }
55:   ]
56: }
57: ```
58: 
59: - `sha256` 打在**文本**上：校验层据此证明「模型引用的这个 id 对应的原文」与序列化时交给模型的是同一份；
60: - `source_sha256` 是**PDF 原件**的 sha256（doc 11 §9.9 要的 page + bbox + 原件 SHA256）；
61: - 切分块的 `parent_id` = 该块**首段的 id**（同一块的所有片段 `parent_id` 相同）；
62: - `piece_start` / `piece_end` 是**码点偏移**，供校验层精确还原该 id 的文本。
63: 
64: ## 3. 模型结果契约
65: 
66: > **权威是 `contracts/schema.json`**（+ 它的散文版 `contracts/prompt.md`）。本节只是索引：
67: > 校验器认的每个位置都能在里面找到 `$defs` 路径。
68: 
69: ```jsonc
70: {
71:   "prompt_version": "1.0.0",
72:   "schema_version": "1.0.0",
73:   "block_count": 4,
74:   "sections": [                       // $defs.section：只有 label / block_ids / ignored
75:     { "label": "contact", "block_ids": ["1", "2"] },
76:     { "label": "work_experience", "block_ids": ["3", "4"] },
77:     { "label": "other", "block_ids": ["5"], "ignored": { "reason": "empty_or_symbol_only" } }
78:   ],
79:   "fields": {                         // $defs.fields：五个键恒在（顶层，不在 section 里）
80:     "name":  { "state": "present", "value": "张三", "block_ids": ["1"] },          // $defs.identity_field
81:     "phone": { "state": "present", "value": "13800001234", "block_ids": ["2"] },
82:     "email": { "state": "absent", "block_ids": [], "reason": "not_mentioned" },
83:     "work_experience": {              // $defs.structural_field：条目在 value[]，不是 entries[]
84:       "state": "present",
85:       "block_ids": ["4"],
86:       "value": [
87:         {                             // $defs.work_entry：事实键平铺，没有 fields 子对象
88:           "company": { "value": "星河科技", "block_ids": ["4"] },   // $defs.fact
89:           "title":   { "value": "后端工程师", "block_ids": ["4"] },
90:           "start":   { "value": "2020.07", "block_ids": ["4"] },
91:           "end":     { "value": "2023.06", "block_ids": ["4"] },
92:           "block_ids": ["4"],
93:           "attribution": "single_block"
94:         }
95:       ]
96:     },
97:     "education": { "state": "absent", "block_ids": [], "reason": "not_mentioned" }   // $defs.education_field
98:   }
99: }
100: ```
101: 
102: 条目数组字段（`work_experience` / `education`）的条目在 **`value[]`**；`education` 的条目键是
103: `school` / `major` / `degree` / `start` / `end`，`work_experience` 的是 `company` / `title` / `start` / `end`。
104: 
105: 引用只有一种写法：`block_ids`（连续且有序；契约里 id 是**字符串** `"12"`，整数也接受）。
106: 不连续 / 逆序 → `BLOCK_IDS_NOT_CONSECUTIVE`。
107: 
108: 封闭集合：
109: 
110: - `label ∈ {contact, summary, work_experience, internship, project, research, education, skill, award, certificate, publication, self_evaluation, other}`；
111: - `state ∈ {present, absent, unreadable}`；
112: - 必填（省略即**拒绝**，没有就写 `absent`）：
113:   - 顶层 `fields`：`name` / `phone` / `email` / `work_experience` / `education`（`$defs.fields.required`）；
114:   - `work_experience` 每个条目：`company` / `title` / `start` / `end`（`$defs.work_entry.required` 的事实键）；
115:   - `education` 每个条目：`school` / `major` / `degree` / `start` / `end`（`$defs.education_entry.required` 的事实键）。
116: - `present` → 必须带非空 `value` + 非空 `block_ids`；`absent` / `unreadable` → 不得带 `value`
117:   （`absent` 还必须 `block_ids: []`）；`unreadable` 还必须带 `reason`；
118: - 每个条目还必须带 `block_ids` 与 `attribution ∈ {single_block, same_row_multi_block}`。
119: 
120: **契约里不存在的位置**（`sections[].fields`、`sections[].entries`、`entries[].fields`、
121: 顶层 `ignored[]`、`entry.block_id` 这类表外键）一律 `SCHEMA_INVALID`——**不静默忽略**，
122: 否则一份「校验通过」的输出可能根本没被检查过。
123: 
124: ## 4. 八条规则 → code
125: 
126: | # | 规则 | 失败即拒绝的 code |
127: |---|---|---|
128: | 1 | id 存在性 | `UNKNOWN_BLOCK_ID` |
129: | 2 | 值必须能在「引用块按序拼接后的文本」里逐字找到（D-30；三种固定归一化见 §4.1） | `VALUE_NOT_IN_BLOCK` / `BLOCK_IDS_NOT_CONSECUTIVE` |
130: | 3 | 每块**恰好**归入一个 section（D-31；或该 section 带合法 `ignored.reason`） | `UNCOVERED_BLOCK` / `BLOCK_DUPLICATED` / `IGNORED_MISSING_REASON` / `IGNORED_BLOCK_REFERENCED` |
131: | 4 | 标签枚举 | `UNKNOWN_SECTION_LABEL` |
132: | 5 | 状态枚举 | `STATE_MISSING` / `STATE_INVALID` / `STATE_VALUE_CONFLICT` |
133: | 6 | phone / email / date 专项 | `PHONE_INVALID` / `PHONE_DIGITS_MISMATCH` / `EMAIL_INVALID` / `EMAIL_NOT_IN_SOURCE` / `DATE_INVALID` / `DATE_NOT_IN_SOURCE` |
134: | 7 | 跨字段一致性（**软**：记 issue 不拒绝） | `WORK_PERIOD_INVERTED` / `WORK_PERIOD_OVERLAP` |
135: | 8 | 不允许省略字段 | `MISSING_FIELD` / `MISSING_ENTRY_FIELD` |
136: 
137: 另外四条（都是「账要平」的机械检查，不是业务判断）：
138: 
139: - `BLOCK_INDEX_INTEGRITY`：索引的 sha256 / `block_no` / 片段偏移与传入的原始块文本对不上；
140:   **或** `block_index` 版本不是 1（`BLOCK_INDEX_VERSION_UNSUPPORTED`）；
141: - `UNREADABLE_MISSING_REASON`：`unreadable` 必须说明为什么读不出来（doc 11 §9.2 红线）；
142: - `BLOCK_IDS_NOT_SUPERSET`：条目 block_ids 必须覆盖它各事实引用的块，字段 block_ids 必须覆盖它各条目
143:   引用的块（`schema.json` `$comment` 不变量 (3)：字段级 block_ids 是 entries 的超集）；
144: - `SCHEMA_INVALID`：形状不对（不是对象 / 数组 / 契约里没有的键 / 事实缺 `value` / 条目缺
145:   `attribution` / `absent` 却引用了块等）。
146: 
147: ### 4.1 值匹配的三种**固定**归一化（D-30 §3）
148: 
149: 块粒度是**视觉行**：一句话会跨块（`#6` 结尾「…佣金结算及分账」+ `#7` 开头「中台等复杂业务。」），
150: PDF 的连字符断行也会把 `semantics` 断成 `seman-` / `tics`。所以 `value` 匹配的对象是
151: **`block_ids` 按序拼接后的文本**，并且只允许下面三种归一化（顺序固定，没有第四种）：
152: 
153: | # | 归一化 | 例子 |
154: |---|---|---|
155: | 1 | **连字符断行**：连字符后接换行（`\n` / `\r\n`）或 `⏎`、再接小写字母时，删掉连字符与换行 | `seman-` + `tics` → `semantics` |
156: | 2 | `⏎` 按它代替的那个换行处理（即按空白） | `13800001234⏎邮箱` → `13800001234 邮箱` |
157: | 3 | 折叠空白：连续空白折成一个空格，再去首尾空白 | `a\n\n  b` → `a b` |
158: 
159: 三条硬约束：
160: 
161: - **只用于匹配，不改原文**：`block_index` 里的文本与 `sha256` 一个字符都不动（D-30 §4，
162:   所以 doc 11 A2 的字符恒等不受影响）；
163: - 块边界只有两种固定拼法：**直接相接**或**当作一个空白**（中文跨行没有空格，英文有词间空格），
164:   两种都试，任一命中即通过；
165: - **不是「语义相等」**（D-32）：`2020年7月` ≠ `2020.07`、`星河科技有限公司` ≠ `星河科技`、
166:   删掉空格 ≠ 折叠空格；这些都必须被 `VALUE_NOT_IN_BLOCK` 拒绝。
167:   规范化留给下游用 `parseDateText()` 做，序列化层不改写任何字。
168: 
169: ### 4.2 覆盖 / 分区的口径（D-31）
170: 
171: - **每个 block 恰好出现在一个 section 的 `block_ids` 里**——重复出现（跨 section 或同一 section
172:   写两次）→ `BLOCK_DUPLICATED`。旧口径「被引用过就算覆盖」已作废：把剩下的 id 全塞进
173:   `block_ids` 只能证明「没漏块」，**不能**证明抽取正确（D-31 §4）。
174: - `ignored` 是 section 上的对象（`{ reason, detail? }`）：存在即表示该 section 的这些块不参与
175:   字段抽取。`reason` 必须非空，且这些块**不得被任何字段 / 条目 / 事实引用**
176:   （`IGNORED_BLOCK_REFERENCED`）。`ignored` 缺 `reason` 时这些块既不算归类也不算排除，
177:   覆盖率会再报一次 `UNCOVERED_BLOCK`。
178: - **字段与 section 之间没有归属绑定**：`prompt.md §6.1` 明写「取值不受 section 限制」，
179:   手机号落在页脚 / 别的章节是常态。所以本层**不再**要求「字段的块属于该字段所在 section」
180:   （旧的 `FIELD_BLOCK_NOT_IN_SECTION` 与契约冲突，已删除）。
181: - 空块也一样要归类，要么被放进某个 section，要么所在的 section 带合法的 `ignored.reason`
182:   （空块不丢是序列化层的承诺，校验层负责盯住它真的被处理了）。
183: - **「连续且有序」只约束用于拼接匹配的引用**（字段 / 条目 / 事实的 `block_ids`）；
184:   `section.block_ids` 是**分区清单**，只要求「每个 id 只出现一次」，允许不相邻
185:   （一个 section 的块被另一个 section 的标题隔开是正常的）。
186: - 条目 / 字段的 `block_ids` 是对分区块的**嵌套引用**，不计入分区次数（否则 work section
187:   里每个条目都会把自己的块「放第二遍」）；但它们之间要满足超集关系（见 §4）。
188: 
189: 数字专项的具体判法：
190: 
191: - **phone**：`^\+?\d[\d\-\s]{6,}$`（任务书给定）；并且把值在原文里的**数字串**取出来，归一化（只留数字）后必须与值一致——
192:   `13800001234` 引用自 `138000012345` 会报 `PHONE_DIGITS_MISMATCH`；
193: - **email**：本地部分 + 带点域名；并且 `value.toLowerCase()` 必须能在原文里找到（大小写不作为凭据）；
194: - **date**：能解析成 `YYYY` / `YYYY-MM` / `YYYY-MM-DD`（也接受语料里的 `2020.07` / `2020年7月`，以及表示开放区间的 `至今` / `present`）；
195:   并且值在原文里必须是一个**完整日期记号**（前后不接数字，避免引用更长数字串的截断）。
196: 
197: > **注意一个刻意设计**：规则 2 要求 `value` 能在**原文（引用块拼接后）**里逐字找到，所以日期必须
198: > **逐字引用原文写法**（`2020.07` 而不是 `2020-07`），邮箱大小写也必须与原文一致
199: > （`EMAIL_NOT_IN_SOURCE` 只在小写后也找不到时补一刀）。D-30 只增加了三种固定归一化，
200: > **没有**增加任何「等价写法」：日期 / 数字的规范化留给下游用 `parseDateText()` 做，本层不改写任何字。

87: 4. 两个版本常量**原样回填**，不得改写、不得自增：`"prompt_version": "1.0.0"`、`"schema_version": "1.0.0"`。
88: 
89: ---
90: 
91: ## 3. 输出骨架（完整，逐键照此形状）
92: 
93: ```json
94: {
95:   "prompt_version": "1.0.0",
96:   "schema_version": "1.0.0",
97:   "block_count": 4,
98:   "sections": [
99:     {
100:       "label": "contact",
101:       "block_ids": ["1", "2"]
102:     },
103:     {
104:       "label": "work_experience",
105:       "block_ids": ["3", "4"]
106:     }
107:   ],
108:   "fields": {
109:     "name": {
110:       "state": "present",
111:       "value": "张示例",
112:       "block_ids": ["1"]
113:     },
114:     "phone": {
115:       "state": "present",
116:       "value": "138 0000 1234",
117:       "block_ids": ["2"]
118:     },
119:     "email": {
120:       "state": "present",
121:       "value": "zhang.example@example.test",
122:       "block_ids": ["2"]
123:     },
124:     "work_experience": {
125:       "state": "present",
126:       "block_ids": ["4"],
127:       "value": [
128:         {
129:           "company": { "value": "示例科技有限公司", "block_ids": ["4"] },
130:           "title": { "value": "后端工程师", "block_ids": ["4"] },
131:           "start": { "value": "2020.07", "block_ids": ["4"] },
132:           "end": { "value": "2023.06", "block_ids": ["4"] },
133:           "block_ids": ["4"],
134:           "attribution": "single_block"
135:         }
136:       ]
137:     },
138:     "education": {
139:       "state": "absent",
140:       "block_ids": [],
141:       "reason": "not_mentioned"
142:     }
143:   }
144: }
145: ```
146: 
147: > 上面这份骨架**本身就是一份合法且自洽的输出**（4 个块全部归类、无遗漏、无重复）——照它的**形状**写，不要照它的内容抄。
148: > 注意 `education` 是 `absent` 且 `block_ids: []`：`absent` 必须为空数组，`present` 必须非空，这是机检项。
149: 
150: ### 3.1 键与类型清单
151: 
152: | 路径 | 类型 | 必填 | 说明 |
153: |---|---|---|---|
154: | `prompt_version` | string（常量 `"1.0.0"`） | ✅ | 原样回填 |
155: | `schema_version` | string（常量 `"1.0.0"`） | ✅ | 原样回填 |
156: | `block_count` | integer ≥ 1 | ✅ | **输入块行数**（不含 `#doc` 行） |
157: | `sections` | array ≥ 1 | ✅ | 块划分，见 §4 |
158: | `sections[].label` | enum（13 项，§5.1） | ✅ | |
159: | `sections[].block_ids` | string[] ≥ 1 | ✅ | 升序、不重复 |
160: | `sections[].ignored` | object | — | `{ "reason": enum(7 项, §5.3), "detail"?: string }`；**存在即表示这些块不参与字段抽取** |
161: | `fields` | object | ✅ | 5 个键全部必填（§6） |
162: | `fields.name` / `.phone` / `.email` | 单值字段 | ✅ | `{ state, value?, block_ids, reason?, reason_note? }` |
163: | `fields.work_experience` / `.education` | 条目字段 | ✅ | `{ state, value?, block_ids, reason?, reason_note? }`，`value` 为条目数组 |
164: | 单值字段.`value` | string | 仅 `present` | 逐字片段，§7 |
165: | 条目字段.`value` | array ≥ 1 | 仅 `present` | 条目数组，§3.2 |
166: | `*.block_ids` | string[] | ✅ | `present` 时 ≥ 1；`absent` 时必须为 `[]`；`unreadable` 时可 0 或多（作证据） |
167: | `*.reason` | enum（12 项，§8） | 仅 `absent` / `unreadable` | `present` 时**禁止**出现 |
168: | `*.reason_note` | string ≤ 200 | — | 可选补充；只能引用原文片段或陈述事实，不得写推断 |
169: 
170: ### 3.2 条目（`work_experience` / `education` 的元素）
171: 
172: `work_experience` 的条目固定 7 个键：
173: 
174: | 键 | 类型 | 说明 |
175: |---|---|---|
176: | `company` | `{ value, block_ids }` | 公司/组织名 |
177: | `title` | `{ value, block_ids }` | 职位名 |
178: | `start` | `{ value, block_ids }` | 起始，逐字 |
179: | `end` | `{ value, block_ids }` | 结束，逐字（`至今`/`Present` 照抄，不折算） |
180: | `block_ids` | string[] ≥ 1 | 本条经历的**整行**来源块（是所有 fact 的 `block_ids` 的并集，且必须是字段级 `block_ids` 的子集） |
181: | `attribution` | `"single_block"` \| `"same_row_multi_block"` | 见 §9 |
182: | `reason` / `reason_note` | 可选 | 本条中有任何 `value` 为 `null` 时**必须**给 `reason` |
183: 
184: `education` 的条目同构，只是把 `company`→`school`、`title`→`major`，并**多一个** `degree`（学历/学位，如 `本科`/`硕士`/`B.S.`）：
185: 
186: ```
187: { "school": {...}, "major": {...}, "degree": {...}, "start": {...}, "end": {...},
188:   "block_ids": [...], "attribution": "...", "reason"?: "...", "reason_note"?: "..." }
189: ```
190: 
191: **条目顺序 = 原文阅读顺序**，不得按日期排序、不得把最新的提到最前。
192: 
193: ---
194: 
195: ## 4. 块归类：三不变量
196: 
197: | # | 不变量 | 机检方式 |
198: |---|---|---|
199: | **S1** | 每个块 id 在 `sections[].block_ids` 里**恰好出现一次**；`block_count` = 输入块数；两者并集 = `{"1".."block_count"}` | 集合比对，不重不漏 |
200: | **S2** | 一个块只能属于**一个** section；不得把一个块拆到两节，也不得把多个块合并成"虚拟块" | 同上 |
201: | **S3** | 章节标题所在的块归**它所引导的那个 section**，不单独成节 | 人读 + 顺序检查 |
202: 
203: **顺序**：`sections[]` 按所含最小 id 升序；`block_ids` 内部升序。
204: 
205: **合并规则**：同一 `label` 的**非 `ignored`** 条目，若中间只隔着其它 `ignored` 条目（没有别的**实质**章节），**必须合并成一条**（`block_ids` 因此可以是不连续的，如 `["23","24","25","27"]`）。
206: 
207: ### 4.1 `ignored` 条目怎么摆
208: 
209: | 情形 | 写法 |
210: |---|---|
211: | 被排除的块**夹在某个章节中间**（例如某章节里的一个光秃秃的 `•`） | **每个块单独成一条**，`label` 填它所在章节的 label，`block_ids` 只含它自己，带 `ignored` |
212: | 被排除的块**不属于任何章节**（页眉/页脚水印、文末二维码、平台广告） | **每个块单独成一条**，`label: "other"` + `ignored` |
213: 
214: - **禁止**把 `ignored` 挂在一个含正常内容的 section 上（否则等于把整节内容都标记成"排除"，下游会整段丢弃）。
215: - `ignored` 条目**不打断**合并规则（见上）。
216: 
217: ### 4.2 章节尾部零散块（真实简历里必然出现）
218: 
219: 章节末尾常跟一些不属于该章节的块（孤立的手机号、个人主页 URL、GPA、页码残留）。裁决顺序：
220: 
221: ```
222: ① 整块只有联络信息（孤立手机号 / 邮箱 / 个人主页 URL / 城市），不含任何正文 → 归 contact
223: ② 否则 → 归当前章节（继承上一个标题），不得因此新造 section
224: ③ 整块是符号/页码/水印 → 按 §4.1 置 ignored
225: ```
226: 
227: > 这条**不影响字段抽取**：字段的值从哪里来，看的是值本身出现在哪个块，不是该块被归到哪个 section（§6.1）。
228: 
229: ---
230: 
231: ## 5. 枚举（封闭集合，逐字使用，不得新造/翻译/加后缀）
232: 
233: ### 5.1 `label`（13 项）
234: 
235: | key | 判据（一句话） |
236: |---|---|
237: | `contact` | 身份与联络：姓名、电话、邮箱、城市、主页链接、求职意向；**首页顶部无标题的那一片也归这里** |
238: | `summary` | 成段的职业概述：`个人简介`、`个人总结`、`关于我`、`Summary`、`Profile`、`About` |
239: | `work_experience` | 全职/正式任职：`工作经历`、`工作经验`、`任职经历`、`职业阶段`、`Employment History`、`Professional Experience` |
240: | `internship` | 实习/兼职：`实习经历`、`实习经验`、`Internship`、`Part-time`（**只看标题词**） |
241: | `project` | 以项目/作品为单位：`项目经历`、`核心项目`、`开源项目`、`作品集`、`Projects`、`Portfolio` |
242: | `research` | 以研究课题为单位：`研究经历`、`科研经历`、`Research Experience` |
243: | `education` | 学校+专业+学历+起止：`教育背景`、`教育经历`、`学习经历`、`Education` |
244: | `skill` | 能力清单（非证书）：`专业技能`、`技能`、`技术栈`、`核心能力`、`Skills` |
245: | `award` | 评奖评优：`获奖`、`荣誉`、`奖项`、`奖学金`、`Awards`、`Honors` |
246: | `certificate` | 可凭证的资质：`证书`、`资质`、`认证`、`Certifications`、`Certificates` |
247: | `publication` | 可引用产出：`论文`、`专利`、`发表`、`Publications`、`Patents` |
248: | `self_evaluation` | 主观自评：`自我评价`、`自我介绍`、`Self Evaluation` |
249: | `other` | 兜底：`兴趣`、`爱好`、`附加信息`、`备注`，以及**确实归不进去的真实内容**。**不带 `ignored`** |
250: 
251: ### 5.2 四对必错的边界（按此裁决）
252: 
253: 1. **`work_experience` vs `internship`**：**只看章节标题**。标题写「工作经历」就整节 `work_experience`，即使其中某条是"实习生"。无标题时才看条目内容。
254: 2. **`award` vs `certificate`**：标题含「奖/荣誉」→ `award`（即使也含「证书」，如「荣誉证书」）；含「证书/认证/资质」且不含「奖/荣誉」→ `certificate`。标题是「技能」而里面夹了 `CET-6` → `skill`（标题优先）。
255: 3. **`summary` vs `self_evaluation`**：`自我评价`/`自我介绍` → `self_evaluation`；`个人简介`/`个人总结`/`关于我`/`Profile`/`Summary` → `summary`。
256: 4. **`project` vs `research` vs `publication`**：过程与做法 → `research`（研究章节内）；项目名+职责+成果 → `project`（项目章节内）；论文/专利条目本身 → `publication`。
257: 
258: > **通用裁决**：`ignored` 是「这块不是简历」，`other` 是「这块是简历但我不知道归哪类」。二者不可互换。
259: 
260: ### 5.3 `ignored.reason`（7 项）
261: 
262: | key | 判据（必须全部满足） |
263: |---|---|
264: | `platform_watermark` | 整块**只剩**平台标识（`BOSS直聘 www.zhipin.com`、`BOSS··  www.zhipin.com`、`猎聘`、`智联招聘`、`51job`、`实习僧`、`牛客`…）；去掉平台名 / URL / 页码 / **标点与符号**后不剩任何文字 |
265: | `page_number_or_header_footer` | 整块只有 `第 3 页 / 共 11 页`、`Page 3 of 11`、`3/11` 或重复页眉 |
266: | `qr_code_or_ad` | 二维码占位、扫码投递、平台推广语 |
267: | `empty_or_symbol_only` | 去掉空白与 `•·-—_|/` 后为空 |
268: | `non_resume_document` | 附在简历后的非简历材料（报告/PRD/讲义），或投递说明模板 |
269: | `duplicate_block` | 与另一块**逐字相同**的重复段（页眉/正文重复），且已有一份归入正常 section |
270: | `glyphs_unreadable` | 整块是坏字形（`\ufffd`、`(cid:12)`、控制字符），去掉后不剩可读文字 |
271: 
272: > ⚠️ `BOSS直聘 产品经理` **不是**噪声（真实职位名）；`linkedin.com/in/xxx` **不是**噪声（个人主页，是联系方式）。
273: > ⚠️ 拿不准时**不要** `ignored`：宁可归 `other`。误删 = 静默丢内容，比归类不准更严重。
274: > ⚠️ 带 `ignored` 的块**禁止**出现在任何字段的 `block_ids` 里。
275:

277: 
278: ## 6. 五个字段 + 三态
279: 
280: ### 6.1 字段定义
281: 
282: | 字段 | 取自哪里 | 注意 |
283: |---|---|---|
284: | `name` | 姓名本身 | 只取人名，**不含**职称/公司/分隔符（`张示例  AI Product Manager` → `张示例`） |
285: | `phone` | 完整号码 | 逐字，含原文里的空格/连字符 |
286: | `email` | 邮箱 | 逐字；被 Markdown 包裹（`[a@b](<mailto:a@b>)`）时取 `a@b`，**不得**输出方括号/尖括号 |
287: | `work_experience` | 章节内的经历条目 | 每条 `company/title/start/end` |
288: | `education` | 章节内的教育条目 | 每条 `school/major/degree/start/end` |
289: 
290: **取值不受 section 限制**：只看值本身在哪个块里，不看那个块被归到哪个 section。手机号落在页脚或某个章节末尾是常态——照抄，`block_ids` 指向它真实的来源块。
291: **唯一例外**：带 `ignored` 的块里的文字**禁止**用作字段值（§5.3）。
292: 
293: **没有第 6 个字段。** 年龄、性别、婚育、籍贯、民族、照片**没有位置**——这是刻意的（§10）。
294: 
295: ### 6.2 三态定义
296: 
297: | state | 含义 | 判据 |
298: |---|---|---|
299: | `present` | 原文有**且已读出** | 你**能在某个 block 的 text 里看见**这个值，且能逐字抄出来 |
300: | `absent` | 原文**确实没有提及** | 全文没有任何该字段的内容，且**闸门允许**你说 absent（§6.4） |
301: | `unreadable` | 原文有**但读不出** | 有标签无值、打码、坏字形、只在图像里、跨块拼不出、闸门禁止 absent |
302: 
303: **红线**：`unreadable` **绝不能**当 `absent`。因为下游会拿 `absent` 当"这人没有"的负向信号，而"没读出来"和"没有"是两件事。
304: 
305: ### 6.3 判定顺序（严格按此顺序，前一步命中就停）
306: 
307: ```
308: ① 你能在块里逐字看见这个值？            → present（照抄，结束）
309: ② 有该字段的标签但值读不出/被打码？      → unreadable + label_without_readable_value / value_masked_or_redacted
310: ③ 出现多个互不相同的候选值，原文没择一？  → unreadable + multiple_conflicting_values（禁止择一）
311: ④ 值所在处是坏字形 / 只在图像里？        → unreadable + glyphs_unreadable / image_only_no_text_layer
312: ⑤ 闸门（§6.4）禁止你说 absent？          → unreadable + page_or_block_unread 等
313: ⑥ 以上都不成立（全文真的没有）          → absent + not_mentioned
314: ```
315: 
316: > **注意 ①**：能看见就必须 `present`，**即使 `#doc` 说这份文档读得不全**。闸门只禁止 `absent`，从不禁止 `present`。
317: 
318: ### 6.4 三条闸门（`absent` 的唯一合法条件）
319: 
320: | 闸门 | 触发条件 | 后果 |
321: |---|---|---|
322: | **G1 内容闸** | A 类 code（§1.2）**或** `unread_pages` 非空 | **五个字段全部不得 `absent`**；想标 absent 的改成 `unreadable`，`reason` 按 §1.3 |
323: | **G2 结构闸** | B 类 code（§1.2）**或** `order_verified=false`，且 A 类不成立 | 只有 `work_experience` / `education` 不得 `absent`；`reason` 按 §1.3 的映射表**逐 code 对应**，不许自选 |
324: | **G3 章节缺失闸** | 文中**有**带日期的经历行/教育行，但**没有**对应章节标题，且这些行**没有被任何其它章节认领** | 该字段不得 `absent`；改 `unreadable` + `no_section_heading`，并把那些行放进 `block_ids` 作证据 |
325: 
326: G1 与 G2 同时成立时，**G1 优先**（G1 的覆盖范围更大）。
327: 
328: > **G3 的"认领"怎么判**：`荣誉奖项` 章节里的 `2025.07-2025.10` 属于该奖项，`科研经历` 里的 `2024.11-2026.06` 属于该研究课题——它们已被各自的 section 认领，**不算**"没有对应章节的工作经历行"。只有那种**孤立在公司/职位形态的文字里、却不属于任何已识别章节**的日期行，才触发 G3。
329:

331: 
332: ## 7. 逐字规则（本契约最容易被违反的一条）
333: 
334: > 每一个 `value` 必须是**它所引用的某个 block 的 `text` 的连续子串**，逐字符相等。
335: 
336: 这意味着：
337: 
338: | 禁止 | 例子（❌ 错 → ✅ 对） |
339: |---|---|
340: | 改格式 | `138 0000 1234` → ❌ `13800001234`、❌ `138-0000-1234` |
341: | 补区号/前缀 | ❌ `+86 138 0000 1234`（原文没有 `+86` 就不许加） |
342: | 删/换分隔符 | `2020.07-2023.06` → ❌ `2020/07-2023/06`、❌ `Jul 2020` |
343: | 补零 | `2023.7` → ❌ `2023.07` |
344: | 改全半角 | `２０２３`、`（华东）` → ❌ 转成半角 |
345: | 去空格 | ❌ 把 value 里原有空格压缩/删除 |
346: | 大小写/翻译 | `Backend Engineer` → ❌ `后端工程师`；`后端工程师` → ❌ `Backend Engineer` |
347: | 换破折号 | `–` `—` `～` → ❌ 统一成 `-` |
348: | 把 `\n` 变成真换行或空格 | 块内换行在 text 里是字面量 `\n`（2 字符），value 引用时**保留这两个字符** |
349: | 补全被裁掉的内容 | `138****1234` → ❌ 猜出后 4 位；`138…` → ❌ 补全 |
350: | 输出 Markdown 包裹 | `[a@b](<mailto:a@b>)` 中的邮箱 → ✅ `a@b`，❌ 连方括号一起抄 |
351: 
352: **日期/电话/邮箱是"字符级证据"**：它们在原文里长什么样，输出就长什么样。格式归一化是下游确定性层的工作，不是你的。
353:

381: 简历里「公司—职位—起止」常跨行、跨栏、跨块。**错行 = 经历张冠李戴**，比读错字更严重。

384: |---|---|
