## 2. 产品定义

**一句话**（逐字）：Recruitment OS 是面向企业招聘全生命周期的 Agent-native Recruitment Operating System：用户通过自然语言或结构化工作台提出招聘目标，Agent 理解企业与招聘上下文，动态组织工具、Worker 和工作流，持续推进需求、岗位、人才获取、筛选、面试、评价、决策、Offer 与入职交接；系统自动处理可自动化的事务，**人只在必要的判断、审批和异常处介入**。

**它不是**（六条）：只做简历解析/管理/筛选的单点工具；传统 ATS 页面里加个聊天机器人；让 HR 逐个点击上传复制催办的工具集合；多个平等 Agent 自由通信的 Agent 群；重新建设 HRIS / 企业知识库 / 邮箱 / 日历 / 会议系统；**由模型独立决定淘汰、录用或 Offer 的自动决策系统**。

**核心差异七行**（传统 vs 本系统）：
交互起点（找模块填表 → 描述目标）/ 工作组织（按固定流程 → Agent 动态规划组合）/ 后台执行（页面操作推动 → 事件触发、跨会话跨进程）/ 跨模块协作（HR 接力 → Agent 跨对象协调）/ 异常处理（提醒用户自行判断 → 识别影响、恢复可恢复、只把必要事项交人）/ 上下文（当前页面字段 → 企业背景+标准+材料+历史+决策+实时状态）/ 人的角色（主要操作员 → 目标提出者、监督者、审批者、关键判断者）。

## 3. 使用者与价值

**6 类角色**（同一页也明确候选人"不是本产品的主要工作台用户"）：企业管理员 / 招聘负责人·HR 主管 / HR·招聘专员 / Hiring Manager / 面试官 / 审批人。

**价值验证方向**（逐字要点）：先验证是否真正减少**人工接力、信息搬运、被动等待**，而不是验证 Agent 会不会答题或调工具。观察：可避免人工交接与重复操作是否减少；HR/面试官实际处理时间是否减少；阻塞是否减少；**Agent 输出是否真正进入业务工作流，修改和拒绝的原因是什么**；招聘质量、证据完整性与关键决策是否仍可靠。
**"不预设未经测量的基线和降幅目标。"**

## 4. 人才接入：八类入口（PRD §4.7）

招聘表单（内部/外部/飞书表单）· 岗位投递链接（官网/招聘页/渠道，**仅官方接口、Webhook 或明确授权**）· 招聘平台/ATS（**以官方接口和企业授权为准**）· 企业数据库与 HR 系统（**只接招聘需要的数据，不重建 HRIS**）· 企业协作工具（飞书/钉钉/企微的表单、消息、文件、推荐材料）· 企业邮箱 · 内部推荐/猎头/合作伙伴 · 人工导入（拖拽单份或批量、上传文件夹）。

**五条产品要求**：不同来源进**统一流程但保留各自来源归因**；一次外部事件可能含多个候选人材料包（一封转发邮件三份简历 → **三条独立 Intake Record**）；原始邮件/表单/文件/外部对象引用必须**可追溯关联**；重复投递/重复推送**不得重复创建业务对象**；**每份材料独立状态，一份失败不阻塞整批**。

---

## 5. 批量处理与异步（PRD §4.8）

> 逐字：**"几十份或几百份简历属于正常业务规模，不应要求 HR 逐份唤醒 Agent。"**

要求：接收后**自动创建后台处理任务**；异步、并行、分批；展示**整批进度与每份材料独立状态**；支持**部分完成**（一份失败不影响其他）；失败项提供单独重试与人工处理入口；完成后**汇总需要 HR 关注的候选人、异常和正式决策事项**；**正常后台处理不持续打断用户**——只有需要授权、人工判断、真实歧义或不可恢复异常时才进注意力入口。

---

## 6. 初筛是自动启动的（PRD §4.12）

> 逐字：**"初筛是 Intake / Application 进入后的自动业务处理，不应要求 HR 再次通过聊天告诉 Agent'开始筛选'。"**

材料接收 + Candidate/Application 关联 + 前置条件满足 → **自动启动初筛任务**；综合 Job/Rubric/企业上下文/候选人材料；结构化呈现能力证据、匹配理由、缺失项、风险、待核实；关键结论可回到简历版本与原文；**AI 可推荐并解释理由**，**HR/有权限的人负责正式确认**；**"模型不能仅凭自身评分自动淘汰候选人"**；大批量在后台持续执行、支持进度与失败恢复；结果进统一视图与注意力入口，**"而不是要求 HR 自己整理多个对话结果"**。

---

## 7. JD / Rubric：默认给高质量起点（PRD §4.4 + 05 页 11-12 段）

- **产品/研究侧提前整理成熟模板库**（JD、能力模型、招聘标准），"**不把'寻找模板'完全推给 Agent 临时发挥**"。
- Agent 同时具备网络搜索能力，找公开优质 JD，**必须保留来源、链接、时间、适用性说明**；**"外部参考不能未经判断就变成企业正式标准"**。
- AI 推荐一组能力维度/权重/必需项/加分项/面试重点，**必须给简明理由**，提供合理默认起点；用户可直接采用、调整、删除、补充。
- **默认保持简单**：不把六层配置全暴露成复杂表单；**"复杂企业规则、特殊维度和定制工作流属于按需定制能力，不是所有用户的默认负担"**。
- 正式生效必须**版本化**，后续筛选/面试/决策能回溯当时版本。
- **"一次性修改默认只作用于当前草稿或对象，不能自动升级成团队或企业规则。"**

## 8. 几条默认行为（容易做反）

| 项 | 默认 |
|---|---|
| Application 推进 | **单个候选人按轮次顺序推进**；多候选人**横向比较只发生在共同到达同一决策节点时**（如都完成终面） |
| 同一 Stage 多面试官 | 允许，**各自独立 Scorecard 并行收集** |
| 并行分支 | **默认体验保持线性**；只有明确业务需要且经配置才启用例外分支 |
| 配置层级 | 底层保留六层作用域，**默认 UI 不展开** |
| 候选人自动归并 | **高置信多维匹配且无冲突可自动归并**；真歧义才人工（Git `docs/03`/`docs/10` 仍写旧口径，待同步） |
| 主动需求发现 | **后置**，不设为本轮闭环前置 |

## 9. 建议采纳闭环（12 页）

### 12 条底层原则

事实优先指标后置 · 完整记录建议生命周期 · 保留人类判断与修改轨迹 · 记录提出者与权限上下文 · 版本不可静默覆盖 · **局部反馈不自动升级为全局偏好** · 自动化事件优先 · **默认简单，不让人为埋点额外填表** · 指标不是唯一优化目标 · **原始业务内容与运行遥测分离** · **不记录模型隐藏思维链** · 不重复建设事实库。

### 十类记录

A 业务事实与状态变化 · B 来源材料与证据溯源 · **C AI 生成物与建议（核心增量）** · D 展示/使用/采纳行为 · E 人工反馈纠正 · F 决策与人工覆盖 · G 版本沿革 · H Agent 执行与运行事实 · I 结果与质量 · J 风险异常治理。

### 十三个行为事件（"建议到底有没有被用"）

`generated` / `exposed` / `opened` / `accepted` / `partially_accepted` / `edited` / `rejected` / `deferred·dismissed` / `expired` / `copied·exported` / `applied` / `sent·published·activated` / `overridden`

> 三条硬规矩：**曝光必须单独记录**（后台生成但未展示的不进分母）；**复制/导出只是行为信号，不证明已使用**；**没有外部回执就不能宣称已发送**。

### 采纳率口径（9 个比率）

曝光覆盖率 / 明确接受率 / **实际采纳率（核心）** / 原样采纳率 / 修改后采纳率 / 明确拒绝率 / 未处理·到期率 / 采纳耗时 / 人工覆盖率。
**分母必须排除未曝光生成物。**
**不能误读**：高采纳率可能是有用也可能是没时间审查；低采纳率可能是不合适也可能用户有成熟判断；修改率高不一定是坏事；覆盖率不等于 Agent 错误；**"不能为了提高采纳率而让 Agent 更强势地说服用户，或弱化不同意见"**。

### "实际应用"的定义（按产物）

JD/Rubric = 保存为正式版本并按规则生效；面试问题/模板 = 纳入某轮 Interview Template 或实际准备材料；**邮件草稿 = 通过 Connector 成功发送并取得回执，仅复制到剪贴板不算**；流程建议 = 经确认形成新 Pipeline/Workflow 版本；筛选建议 = 被有权人员采纳为正式阶段操作；Brief = 保存并实际提供给授权面试官；企业偏好 = 经确认写入指定范围的有效配置版本。
**外部动作无法回读或确认 → 记"已提交/结果未验证"，不虚报为已应用。**

### 五级作用范围

`OUTPUT_ONLY → APPLICATION/CANDIDATE → JOB → TEAM/DEPARTMENT → ORGANIZATION`
**默认只改当前对象**；往大范围沉淀必须**明确展示作用范围并由有权限的人确认**；**"不能因为同一用户两次要求改邮件语气，就擅自把它提升成全企业邮件政策"**。

### 优化闭环 8 步

`Observe → Diagnose → Hypothesize → Propose → Review/Approve → Version/Rollout → Measure → Decide`

**自动化边界**：低风险运行参数/重试/调度可在预先授权范围内自动调整并留版本与回滚；邮件措辞/默认模板/工作台偏好可由 Agent 建议、用户确认后应用；**岗位标准、筛选规则、Pipeline、评分权重、招聘政策必须负责人确认**；权限、淘汰规则、正式决策、Offer 条件、对外发布必须既定审批。

**实验边界（逐字）**：**"不能为了 A/B 测试而未经批准地随机改变候选人的筛选条件、考察流程或评价条件。"** 优先用历史基线、版本前后对比、风险抽样、批准后的小范围试运行。

### P0/P1/P2

**P0 从第一天就要留下的事实**（漏了通常无法补回）：统一事件关联（稳定 ID/业务对象引用/Actor·Role/来源/时间戳/correlation·causation）、业务状态变化与任务·Attempt·Tool Call·Effect·Receipt、**AI 重要输出的类型/内容版本/来源证据/所用模型·Prompt·Rubric·Workflow 版本**、**建议是否真正曝光**、接受/部分接受/修改/拒绝/暂缓/关闭、**修改前后版本与 Diff**、正式应用到哪个业务对象、人工最终决策与是否覆盖 AI、后续业务结果关联、有意义的错误与纠正、数据分类与保留规则。
> 逐字：**"P0 的目标是保证数据将来可分析，不代表 v1.0 必须同时建设完整分析大屏或自动优化 Agent。"**
**P1** 统一反馈入口与分类、作用范围确认、变更提案与审批/版本差异/回滚、采纳分析视图、抽样复核、版本前后对比与试运行。**P2** Agent 主动发现瓶颈与标准偏差、提优化方案、发现质量漂移、授权范围内低风险自适应、企业经验方法库。

## 10. 三种触发方式与优先级（PRD §6.2）

| 触发 | 例子 | 优先级 |
|---|---|---|
| 用户发起 | 提需求、查候选人、要求调 JD | 基础能力 |
| **已发生业务事件** | 新简历、转写生成、Scorecard 提交、候选人回复、日历变化 | **核心优先级** |
| 系统主动发现 | 离职/调岗/编制变化推断需求；主动找人才线索 | **后续优先级** |

> 逐字自动化原则：**"已经发生、能够确定处理的业务事件，应尽可能自动推进；需要人判断、授权或处理真实歧义的事项才交给人。"**

**Agent 工作循环**：`Observe → Understand → Plan → Act → Verify → Replan`。

## 11. 产品验收八条（PRD §15）

> 逐字：**"每项功能不能只以'页面存在''模型回复成功'或'Agent 自报完成'作为验收。"**

1. **用户目标可完成**：目标角色能通过自然语言或工作台完成明确业务任务
2. **业务结果真实落地**：写入正确业务对象，状态与责任人明确
3. **自动化符合预期**：已发生的确定性事件能自动触发；真正需人判断的才进人工入口
4. **证据与版本完整**：关键结论能回到来源，配置与产物能回溯版本
5. **人工职责正确**：该谁审批、评价、决策，边界清楚
6. **异常可处理**：重复事件、失败、授权失效、部分完成、外部未知结果都有明确状态与恢复路径
7. **外部能力诚实**：真实接入、手动交接、模拟数据、未接通能力不混淆
8. **前序版本不回归**：新增能力不能破坏已验收的旧版本 Golden Path

## 12. 版本路线

| 版本 | 状态 | 交付结果 |
|---|---|---|
| **1.0 Core Recruitment Execution** | **Frozen** | HR 从材料走到证据化筛选、面试、转写、独立评价与正式人工决策 |
| 2.0 Hiring Demand & Role Planning | Proposal | 需求 → 获批且定义清楚的 Job（Requisition、审批、Job Kickoff、Role Calibration、成功画像、标准） |
| 3.0 Job Definition & Publishing | Proposal | 完整 JD 编辑、渠道文案、审批、Posting、外部状态回读 |
| 4.0 Sourcing & Talent Activation | Proposal | Prospect、授权寻访、内推、人才库激活、Sourcing Activity、Communication Record |
| 5.0 Multi-source Intake & Pipeline Ops | Proposal | 邮箱/表单/批量导入/授权 ATS·平台接入、统一 Intake、扩展 Pipeline |
| 7.0 Offer & Onboarding | Proposal | Offer 版本、审批、发送、响应、Onboarding Handoff |
| 8.0 Talent Intelligence & Process Optimization | Proposal | 人才复用、分析、采纳反馈、模板/Rubric/Pipeline 优化、版本试运行与回滚 |
| 10.0 Enterprise Ops & Integrated Context | Proposal | HRIS/组织上下文同步、企业连接器、运营与部署 |

**六条交付原则**：每个版本是前一版的累积增强，**不能破坏已验收闭环**；**任意版本停止开发，前一个已验收版本仍可运行**；不要求每个整数版本都存在（**不包含 6.0、9.0**）；后续版本实现前必须有独立 Release Brief；**工程 WP / Gate / Wave ≠ 产品版本**；完成一个模块 ≠ 完成一个产品版本。

**v1.0 冻结边界（PRD §13.2）**：预置企业/部门/团队/Job/版本化 Rubric；文件·Fixture Intake + 原始材料 + Intake Record·Asset + Resume Version；Candidate 识别/重复处理/Application 分离；证据化初筛；Interview + 两位面试官 + Meeting Binding；**真实飞书会议转写接入为 P0，仅用 Fixture 不能通过演示验收**；完整转写 + 结构化 Interview Record + 证据回链；两位面试官独立 Scorecard 且与转写并行；Evaluation 汇总 + 正式人工 Decision + Next Round Brief；持久化任务进度、执行记录、角色视图、最小 Inbox、基础 Agent Chat；本地工作台与 Worker 能力。

## 13. 明确后置 / 范围外（PRD §14）

面向求职者的公共招聘市场或独立候选人门户 · **模型独立做最终淘汰/录用/Offer 决策** · 多个平等 Agent 自由通信的 Agent Swarm · **自研 ASR、说话人分离、通用队列、通用调度器或 HRIS** · 未经官方授权的平台抓取/自动联系/自动发布 · 为低频长尾建复杂基础设施（如把会议室预订作为排期默认前提）· 为展示数据建重复指标库/重复候选人档案/重复任务事实 · 本地 Demo 阶段提前建生产级多租户 SaaS、SSO 与企业运维 · 全双工语音作为核心闭环前置。
