## 二、产品负责人定的两条原则（比任何功能都重要）

1. **Agent 是动态的，不是死程序。**
   工具覆盖不了所有招聘场景，但只要**底层数据、链路、闭环**都在我们手里（候选人、面试官、转写、简历、流转记录、判断记录、执行记录），Agent 就能用模型能力去分析和应变。
   → 推论：**穷举场景工具 = 把 Agent 写成程序 = 丢灵魂**。要做的是"原子能力 + 软 SOP + 全上下文"。

2. **上下文就是数据。**
   候选人过了几轮之后，积累的就是一堆结构化 + 非结构化的上下文；横向对比、复盘、纠偏，都是"把这些上下文喂给 Agent"。
   → 推论：**读得全**比"多做几个分析工具"更重要。

## 三、明确不做（再被问到就指这里）

| 不做 | 为什么 |
|---|---|
| Offer 系统 / 入职办理系统 | 属企业人事系统，不是我们（`docs/24 §4`） |
| 多面试官联合会审 / 分歧仲裁 | 流程是线性的，各自对自己那轮负责（`docs/24 §3`） |
| 专门的"分歧聚合"对象 / "横向对比"工具 | Agent 读上下文即可，不需要业务对象（`D-155.4`） |
| 主动捞人 sourcing / 转岗推荐引擎 | 不主动提（`docs/24 §4`） |
| 多租户邮箱托管 | 先做一个账号一条真链（`D-155.5`） |
| 把 Agent 写成"每个场景一个按钮" | 违反原则二（`D-155.3`） |
| 站内催办 / 拉会协调 | 沟通在系统外，我们只记结果（`docs/24 §4`） |

## 四、这一轮真正定下来的三件事（及去处）

1. **执行线定位**：真相层自建 PG、执行载体用 DSH、设计形状只借 superagent 的两点半。
   → `docs/27`（审查）、`docs/28`（模块选型）、`D-149`~`D-154`。
2. **验收标准**：六条门是上位，"怎么验到"落成逐条判据（含负例、含当前差距）。
   → `docs/29`、`D-152`。
3. **邮箱连接器**：收发都做；无"通吃连接器"，统一层是 IMAP/SMTP + 认证适配；发信走"按范围授权"，Offer 永远人点。
   → `docs/31`、`D-155.5`。
