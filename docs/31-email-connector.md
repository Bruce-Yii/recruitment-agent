# 31 · 邮箱连接器：调研结论与落地方案（2026-11-18）

> **为什么有这份**：产品负责人指出——简历的第一入口就是邮箱，面试通知、初筛结果、Offer 代发也都走邮件；这是基础能力，不是"做 Offer 系统"。
> 依据：`docs/17` **D-155**。验收对接：`docs/29`（外部事实诚实 V4 / 人的闸门 V3 / 幂等）。
> **二次核对钩子**：文中外部事实（协议停用时间等）标了来源，落地前按你的环境再核一次。

---

## 1. 一句话结论

**没有"一个连接器通吃所有邮箱"的成熟开源方案；真正的统一层是 IMAP/SMTP 协议本身，差异全在"认证"。**
所以我们要做的不是"找一个大一统连接器"，而是：**一个 IMAP/SMTP 客户端 + 每类厂商一个认证适配器 + 统一的消息/附件/去重层**。

---

## 2. 事实：国内主流邮箱怎么接（认证方式决定一切）

| 邮箱 | 收（IMAP） | 发（SMTP） | 认证 | 备注 |
|---|---|---|---|---|
| QQ 邮箱 | `imap.qq.com:993` | `smtp.qq.com:465` | **授权码**（设置里开启 IMAP/SMTP 后生成，当密码用） | 最常用；必须用授权码，不是登录密码 |
| 163 / 126 | `imap.163.com:993` | `smtp.163.com:465` | **授权码** | 同上 |
| 腾讯企业邮（exmail） | `imap.exmail.qq.com:993` | `smtp.exmail.qq.com:465` | 客户端专用密码 / OAuth2 | 企业场景最常见 |
| 阿里企业邮 | `imap.qiye.aliyun.com:993` | `smtp.qiye.aliyun.com:465` | 密码 / 专用密码 | — |
| 公司自建 / Exchange | 视域名而定 | 视域名而定 | 密码 / OAuth2 | 需要管理员给应用权限 |
| Gmail | `imap.gmail.com:993` | `smtp.gmail.com:465` | **OAuth2**（或应用专用密码，取决于账号策略） | 个人号应用专用密码仍可用；Workspace 多半要 OAuth2 |
| Microsoft 365 / Outlook | `outlook.office365.com:993` | `smtp.office365.com:587` | **OAuth2 强制** | **Basic Auth 于 2026-04-30 全面停用**（微软官方公告），应用专用密码一并失效（外部事实，落地前复核） |

**结论**：国内场景"授权码/专用密码"能覆盖绝大多数；**国际场景（尤其 Microsoft 365）必须 OAuth2**。这就是"统一连接器"的真实形状——**协议统一、认证不统一**。

## 3. 组件选型（复用优先，R1）

| 层 | 选什么 | 为什么不自己写 |
|---|---|---|
| 收件 | `imapflow`（或 `node-imap`） | IDLE/重连/编码这些坑不值得重造 |
| 解析 | `mailparser` | MIME/附件/多编码解析是硬骨头 |
| 发件 | `nodemailer` | SMTP 认证/退信/TLS 成熟 |
| 认证 | 自写薄适配层：授权码 / 专用密码 / OAuth2 | 没有通用件能同时覆盖国内外 |
| 参考实现（只读借鉴） | `magicmail`（私有化多邮箱聚合，IMAP IDLE 推送）、`Cypht`（开源 webmail 聚合） | 看它们怎么处理多账号与去重 |
| 商业备选 | Nylas 等统一邮件 API | 省 OAuth 工程，但**数据出域 + 收费**，与"本地/私有化"路线冲突，v1.0 不用 |

> DSH 侧：MCP 生态里有邮件服务器，但成熟度参差；**本产品沿用"自建轻连接器"的路子**（与飞书连接器同构），不为了"用 MCP"而用 MCP。

## 4. 我们要做的两条真链（先窄后宽）

### 4.1 收件箱（P0，简历入口）

```
IMAP 只读轮询（一个账号，先支持授权码）
  → 拉新邮件（按 UID 记位点，重启不重放）
  → 解析（主题/发件人/时间/正文/附件）
  → 附件落盘 + sha256
  → 复用现有 intake：类型按内容嗅探 → 去重（同一 sha 不重复建档）→ 证据闸门
  → 落库：邮件事实 + 附件事实 + 候选人/申请（复用现有）
```

- **幂等**：以 `message-id + 附件 sha256` 去重；同一个附件重复到达不重复建档（与既有 S6 幂等一致）。
- **诚实标签**：`provenance=LIVE`、`trigger=EVENT`（收到即触发）、`connection=CONNECTED`；读失败要如实标 `NOT_CONNECTED` / `AUTH_REQUIRED`。
- **不做**：不建"邮箱托管"、不做多租户、不代收非招聘邮件。

### 4.2 发信（通知 / Offer 代发）

```
Agent/人 触发 → 组装（收件人 + 模板 + 变量）→ 预览
  → 人工确认（真界面点；Agent 不能自点）
  → 落 outbox（幂等键 = application_id + 模板 + 版本）
  → SMTP 发送 → 回执状态（DRAFT/SENT/FAILED/退信）
```

- **幂等**：同一幂等键重复提交不发第二封（这是"外部写"的硬要求，`docs/24 §5`）。
- **闸门**：发信是外部写，必须真人确认；Agent 只能准备草稿。
- **Offer 邮件**：只是"用这个通道发一封信"，**不是 Offer 系统**——不建薪资审批流、不建入职流程（D-155.1）。

## 5. 关键风险（落地时要盯）

1. **重复拉取**：IMAP 按 UID 记位点，必须持久化；否则重启会重放整箱。
2. **附件安全**：只落已知类型、限制大小、校验 sha；压缩包与宏文档按"读不出来"处理，不猜。
3. **认证失效**：授权码会过期/被改；要区分 `AUTH_REQUIRED`（可修）与 `NOT_CONNECTED`（网络）。
4. **发信退信/进垃圾**：SPF/DKIM 属客户域名侧；我们只做"发出去了 + 回执"，不承诺送达。
5. **PII**：邮件正文可能含身份证/薪资，按 R7 不落原文全文，只留必要摘要 + sha + 定位。

## 6. 验收判据（对接 `docs/29`）

| 判据 | 怎么验 |
|---|---|
| 真邮件进得来 | 一个真实合成账号，投一封带附件邮件 → 库里出现邮件事实 + 附件 sha256，两次读取一致 |
| 幂等 | 同一封邮件重复投递/重复轮询 → `resume_version` 不翻倍 |
| 断连如实 | 授权码改错 → `AUTH_REQUIRED`，零写入 |
| 发信要人点 | Agent 单独不能发；人在界面点了才有 `SENT` |
| 发信幂等 | 同幂等键重复提交 → 只有一封 |
| 外部事实诚实 | `provenance/trigger/connection` 三维与实际一致 |

---

## 7. 建议的落地顺序

1. **收件箱最小链**（一个账号、授权码、只收附件）——先证明"简历从邮箱进来"这条真链。
2. **发通知邮件**（复用同一 SMTP；人工确认 + 幂等）。
3. **OAuth2 适配**（Gmail / Microsoft 365）——等有真实客户用这两家再做。
4. **多账号/多租户**——不做，除非客户明确要求（另立裁决）。
