# 26 · 产品说明（这是什么、给谁用、现在能做什么）

> **这份是"产品说明"，写给要理解产品的人**：招聘负责人、HR、面试官、新加入的同学、外部评审。
> 它与工程文档的分工：**这里讲"用户看到什么、业务怎么走"**；怎么实现、怎么证明看 `18`（怎么跑）/ `24`（验收口径）/ `17`（裁决）。
> **口径冲突时以 `24` 为准**；本文件不定义验收标准。

---

## 1. 一句话

**把散落在简历、面试官脑子里、聊天记录里、Excel 里的招聘上下文，按「人」串起来；用 Agent 把它变成人一眼能看懂、能快速判断的东西；判断权永远在人手里。**

它不是招聘平台，不是人事（HRIS）系统，不是沟通工具，也不是流程引擎。

---

## 2. 谁用、用来干什么

| 角色 | 他要干的事 | 系统给他的东西 |
|---|---|---|
| **招聘负责人 / HR** | 判断"这个人值不值得往下走"，并留下依据 | 材料结构化 + 对着岗位标准的逐条对照 + 自己拍板的一步操作 |
| **面试官** | 在有限时间里问到点上，并独立给出评价 | 材料摘要、这一轮可以参考的重点、上一轮实际聊了什么 |
| **用人经理** | 看进展、看关键判断、对结果负责 | 卡在哪、谁在等、关键决策与依据 |
| **管理员** | 接上外部（飞书等）、配岗位标准 | 连接器状态与配置；配置问题在界面上说人话 |

**一句话的体验目标**：HR 打开一条申请，**不用翻 PDF、不用问人、不用记编号**，就能决定要不要往下走；面完之后，**半年后还能查清"当时为什么这么决定"**。

---

## 3. 它解决的是什么问题

真实招聘里最痛的不是"缺系统"，是**上下文散落**：

- 简历在邮箱/招聘网站，格式各异；
- 岗位标准在用人经理脑子里、在 JD 里、在上一轮面试的记录里；
- 面试官各问各的，下一轮不知道上一轮问了什么；
- 面评在飞书文档里，决策理由在 HR 的脑子里；
- 一件事要问一圈人才能拼出全貌。

→ 所以产品做三件事：**按人收拢上下文 → 变成人能快速读懂的东西 → 判断留给人并留痕**。
→ 所以**不是**再建一个"流程更长的系统"。

---

## 4. 一条链怎么走（用户视角）

以「后端工程师」岗位、一位候选人「张样例」为例：

1. **简历进来** —— 系统认出真实文件类型、读出内容；读不出的地方如实说"没读出来"，**不猜、不要求人补录**。
2. **HR 打开这条申请** —— 左边是材料（每条能点到原文"第几页第几行"），右边是对着岗位标准的标注：哪条要求有对应、哪条没有、哪条读不出来。
3. **初筛决定** —— Agent 给逐条对照和一句建议，并明确写着"这是建议，不是决定"；**人拍板**：通过 → 这条自动进入面试阶段；不通过 → 这条**直接结束**（不会还挂在"在办"，也不会再提示你安排面试）。
4. **约面试** —— 系统依据招聘事实和日程空余**给建议时间**；**不在系统里替人拉会协调**（沟通在系统外发生，我们记录结果）。
5. **面试官进场** —— 打开这场面试就能看到：材料、这一轮可以参考的重点（**参考不是指令**，怎么问是面试官的职权）、以及**紧邻上一轮实际发生了什么**（按岗位标准：聊到了哪些、评了什么、哪条没覆盖）。
6. **面完** —— 转写进来（有就说有，没有就说"还没有转写"），面试官各自独立提交面评，互不影响。
7. **决策** —— 面评齐了才汇总，Agent 摆事实不讲结论；**人做决定并留痕**：谁、何时、依据哪份材料、哪版岗位标准。

**界面长什么样**：工作台（我的待办：待初筛、我的面试、逾期面评、待审批、卡住的任务）+ 申请详情 + 面试详情。UI 设计仍在定稿中，**当前布局不保证是最终形态**。

## 5. 现在（v1.0）能做什么

- ✅ 简历接入与解析：PDF / DOCX / RTF / 纯文本；读出字段三态（读到 / 没有 / 读不出）+ **可复核的原文引用**（源文件哈希 + 定位唯一 + 原句逐字命中）。
- ✅ 岗位与岗位标准：创建岗位、生成标准草案、审批生效、按版本钉住（谁能改、改了影响谁，都留痕）。
- ✅ 初筛：对标准逐条对照、给一句建议（标明"不是决定"），人做"通过 / 不通过"，**一步到位**且可追责。
- ✅ 面试：排期建议、面试官视图、**前置轮次摘要 + 本轮参考**、面评独立提交、按轮推进。
- ✅ 转写：飞书会议转写读取（一条真实链路），没有就如实说没有。
- ✅ 决策：汇总面评与分歧、人的决定、决策依据与版本可查；被拒申请自动结束。
- ✅ 看得见：原文按需点开（不把 PDF 当主视图）、会话计量（模型自己有多少上下文/花了多少）、任务与卡住事件状态。
- ✅ 长任务可恢复：任务跨会话继续，不因为关窗口就丢。
- ✅ Agent 能力：30 个业务工具（读上下文/写业务/交人决策），工程工具（shell/文件系统等）在产品会话里**不注册**。

## 6. 现在**不做**（别去找，也别验收这些）

**不做**（不是产品方向）：主动捞人/sourcing、Offer 与入职办理、企业人事系统具体对接、系统内沟通协调（拉会/催办）、独立"人才沉淀"模块、角色×视图矩阵、多租户/云端部署/合规留存、报表看板。

**这版还没做**（等条件）：前端两件（工作台首页"今天干什么"、原文阅读器）正在接；真实招聘网站投递接入、飞书日程/会议自动化、线下录音转写。

**已定（2026-11-18）**：初筛默认给一句倾向性建议，并明确写"这是建议，不是决定"；不给分数、不做排名。

## 7. 和别的系统有什么不一样

| 常见做法 | 我们为什么不这么做 |
|---|---|
| 再来一个 ATS（更长的流程、更多必填字段） | 痛点不是流程短，是上下文散；所以我们先做"按人串起来" |
| 让 AI 直接筛人、打分、给结论 | 对人的判断涉及责任，**Agent 只做辅助**；决定必须是人做的，且能追责 |
| 让人把系统没读出来的字段手工补齐 | **收到什么就是什么**；读不出如实说，不制造"填表负担" |
| 系统内做沟通（站内信、催办、拉会） | 沟通天然在系统外（飞书/微信/当面），我们只**记录结果**，不做第二套沟通 |
| Fixture/演示数据冒充真实 | 外部事实必须诚实标注；演示数据只用于开发和验收，**不作验收依据** |

## 8. 现在的真实状态（别被文档里的愿景误导）

- **阶段**：本地开发 / 验证中，**尚未进入产品交付**；当前用免费模型（HY4）跑，不代表交付口径。
- **能演示的**：上面 §4 那条链在演示岗位上能走通（含演示数据）。
- **已知不足（诚实说）**：
  - 工作台/面试官页面的**视觉与布局未定稿**，现在能用但不代表最终样子；
  - 演示库的岗位标准是**演示数据**（已修正为"可执行"版本，但内容刻意简单）；
  - 部分页面还在接后端（今天要干什么、原文阅读器）；
  - 没有真实客户环境、没有多租户、没有权限体系（v1.0 明确不做）。
- **验收**：由独立窗口按六条门判定（上下文闭环 / 辅助且不傻逼 / 人的闸门 / 外部事实诚实 / 看得见 / 长任务可恢复），**尚未给出 PASS 结论**。

## 9. 术语（人话对照）

| 词 | 人话 |
|---|---|
| **申请（application）** | 一个人投了一个岗位这件事 |
| **阶段（S6→S10）** | 简历接入 → 初筛 → 面试 → 转写 → 决策；只是**业务标签**，不是模块清单 |
| **岗位标准（rubric）** | 这个岗位"什么样算合格"的条目集合，有版本、要人审批 |
| **对应（原文引用）** | 岗位标准里某一条，在材料里找到的那句原话：哪份文件、哪个位置 |
| **面评（scorecard）** | 面试官对候选人这一轮的独立评价 |
| **决策（decision）** | 人的正式判断（通过/不通过/待定等），带依据、带版本、可追责 |
| **上下文** | 系统围绕"这个人这次申请"攒起来的全部事实 |

## 11. 2026-11-22 现行 v4 基线同步

- **唯一前端形态**：独立整页 `/recruitment/app`（暖纸编辑感决策工作台，旧 DSH 侧栏入口已退役 D-181），包含工作台首页待办、岗位漏斗与标准审批/关岗、候选人详情与原文磁吸对照、多候选人横向对比及面试官视角（`#/interviewer`）。
- **对话 × 画布联动**：伴随式对话栏保持 **19 只读 / 0 写工具**，通过单轨 `ui_action` 支持导航、页内聚焦、建议弹窗与 5 类高频动作对话内暖纸确认卡（仍由真人点击走既有写合同）。
- **自动化备料与只读增强**：已落地上传入库自动触发初筛评估摘要（不写决策）、IMAP 邮箱定时轮询与自动分岗（env 控制）、转写入库自动生成待面试官核对的面评草稿（不代提交）、人工逐条纠偏、历史人才库只读再发现与疑似重复投递只读提示。
- **仍属下一阶段**：真实飞书日历/妙记改绑真机实测（待凭据）、生产登录/独立域名/多租户（D-178）及候选人自助选时段（见 [`docs/40`](40-lifecycle-gap-roadmap.md)）。
