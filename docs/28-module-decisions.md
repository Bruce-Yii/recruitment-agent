# 28 · 模块级选型：把产品链路映射到工程实现（2026-11-18）

> **这份是选型建议，不是裁决**。方法照产品负责人说的：**拆模块 → 逐个跟成熟方案比 → 选最优 → 说清理由**。
> 上位文档：`docs/24`（产品认知与验收口径）、`docs/27`（执行线审查 + 三条线对照）。
> 附：`work/research/2026-11-18-dsh-native-execution.md`（DSH 原生逐条证据）、`2026-11-18-superagent-execution-model.md`（prototype 原句）。
> **前端不在本文范围**（界面实现不归总控）。

---

## 0. 一句话结论

**"账本自建（PG）、手用 DSH、图纸借 prototype"这个判断成立**，而且拆到模块级之后更清楚：
- **真相层**（谁拥有业务事实）——只有一项能选：自建 PG。DSH 的真相是会话日志+进程内存，prototype 的真相是单机 SQLite，两者都不能承担"跨进程、可追责、可审计"。
- **执行载体**（谁来跑）——全用 DSH，不自研。
- **设计形状**（照着谁的结构做）——只借 prototype 的 3 个点，其余不借。

**再吸收更多 prototype 的东西，收益小于代价**，因为它最长的板（效应先存后做）我们还没有使用场景，它最弱的板（单机 SQLite、重启判死）正好踩在我们的产品底线（可追责）上。

## 2. 模块级选型表（这张表就是答案）

判据列固定四问：**① 产品要求是什么 ② 候选有谁 ③ 选谁 ④ 为什么不选别的**。

### A. 领域与真相

| 模块 | 产品要求 | 候选 | **选** | 为什么不选别的 |
|---|---|---|---|---|
| 业务对象（候选人/岗位/申请/面试/决策） | 跨进程、可追责、多表事务、可审计 | 自建 PG 表 / prototype 的 Ticket+SQLite / DSH 会话日志 | **自建 PG** | SQLite 单机不能多实例、不能审计；会话日志不是数据库（`dsh-subagent/README.md:240` 明说不协调两个进程） |
| 状态机（阶段/生命周期/决策唯一性） | 同一时刻只有一个真相；并发写不能互相覆盖 | 自建（行守卫触发器 + `uq_decision_current`）/ 应用层乐观锁 | **自建 + 库约束**（现状） | 把不变量放应用层 = 换个入口就绕过去；放库里才是硬约束 |
| 追溯链 | 一个 id 串起 事件/任务/尝试/会话/副作用/决策 | 自建 `trace.ts` / prototype 的 `thread` 表 / DSH 会话日志 | **自建**（现状） | 会话日志是单会话视角，跨对象追溯做不到 |
| 业务动作的审批（rubric 批准、面评、决策） | 真人、真界面、可追责、拒绝零写入 | PG 闸门 + Host Action / DSH `ctx.approval` / prototype `Attention` | **PG 闸门**（现状） | DSH approval 只在 open turn 内 one-shot、pending 在内存（`dsh-user-approval/README.md:164-168`）；Attention 是原型单机对象 |

### B. 材料与理解

| 模块 | 产品要求 | 候选 | **选** | 为什么不选别的 |
|---|---|---|---|---|
| 文档解析（PDF/DOCX/RTF/文本） | 不猜类型、保留定位、可复核 | 自研 converter（PyMuPDF/striprtf）/ 现成 PDF SDK / 大模型直读 | **converter（现状）** | 模型直读不能满足"定位唯一 + 逐字命中"（D-110）；换 SDK 要有 gap proof（R1） |

### C. 执行与调度（**这次研究的重点**）

| 模块 | 产品要求 | 候选 | **选** | 为什么不选别的 |
|---|---|---|---|---|

| 认领与并发 | 多实例不抢同一任务 | PG `FOR UPDATE SKIP LOCKED` + 唯一租约 | **现状** | 不需要队列中间件（D-109 已论证） |
| 进程内调度节拍 | 一个实例派发、多实例不重复 | PG advisory lock + 2s tick | **现状** | 用 file lock / Redis 都是加依赖 |

## 3. "要不要更吸收超级架构"——逐条算账

产品负责人问的其实就是这张账。**结论：只有 2 个点值得吸收，1 个点要先定性。**

### 3-1（先定性）效应队列 / 出站：**保留薄桥，还是退役？**

- **它值钱的地方**：副作用"先存后做"、失败按 2s→60s 退避、三振、回执对账——这是原型最成熟的一块（`VENDORED.md §3.1`）。
- **它今天没用上**：v1.0 没有任何"系统自己去写外部系统"的场景（飞书是**读**，导入是人点的）。真 Host 跑完整链后 `engine_*` 全 0 行。
- **两种走法**：
  - **退役**：拆 `index.ts:651-676` 装配、`engine_*` 表标"保留未用"。好处：少一层概念、少一张永远空的表；代价：将来做外发要重做一次。
  - **保留为薄桥**：明确写"它只负责 launch/delivery 踢 tick，reply 有外发才启用"，并在台账登记。好处：外发能力现成；代价：库里长期有一组空表，容易被误读成"有这条线"。
- **我的建议：退役（或至少拆到"未启用"）**。理由：
  1. `launch`/`delivery` 现在等价于一个 2 秒 pump，而 `router.tick()` 本来就有 tick loop 在做同一件事（`tick_interval_ms: 2000`）——**这层今天没有存在理由**；
  2. **它是一条第绕过 advisory lock 的 tick 路径**：tick loop 持 `recruitment:tick` 咨询锁保证"多实例只有一个派发者"，而 engine 的 `drive()` 直接调 `router.tick()`，**不检查这把锁**。今天因为 `engine_*` 恒 0 行所以无害；一旦真有 effect，多实例部署下就多了一个不受锁约束的派发者——这是"看起来有唯一派发者、实际没有"的假不变量；
  3. 代码不会丢：`VENDORED.md` 记着每个文件的上游路径与改动，等真要做外发再按台账接回来。

### 3-2（值得吸收）"人"的槽位语义

- 原型的规则：`maxWorkers` 个普通槽 **+ 1 个专门留给人的槽**，"人的消息永远挤不掉正在跑的活"（`docs/03:377` 引原文）。
- 我们的差距：`router.tick()` 一次只派一个、按 `priority, next_run_at, created_at` 排序——**"人现在在等的那一下"和"后台批处理"没有区别**。批量导入 50 份简历时，HR 点开一条申请的操作会排在一堆解析任务后面。
- **成本**：在认领排序里加一档（例如 `priority` 已有 1–5，把"人在等"的任务标 1）。**不动架构。**
- **结论：吸收。**

### 3-3（值得吸收）重开 attempt 时写 recovery note

- 原型的做法：运行中的 Assignment 重启判死，重开时**附一条 recovery note**（"上次做到哪、有什么没确认"），最老的工单先开。
- 我们的差距：新 attempt 只知道"上次失败了"，不知道"上次做到哪"。`task-context.ts` 已有 UNKNOWNS 机制，但没有把**上一次 attempt 的 summary/错误**喂进去。
- **成本**：任务书里多一段"上次尝试"（读 `task_attempt` 最近一行）。**不动架构。**
- **结论：吸收。**

### 3-4（不吸收）Ticket / Mandate / Assignment 领域模型

我们的聚合根是 `application`（人事合一），Ticket 是"一张工单"，语义错位。硬搬会多一套领域概念，且 prototype 自己说它是"reference only"。

### 3-5（不吸收）Attention 作为闸门

我们已经用 PG 闸门 + 前端待办表达"人要看的东西"；Attention 是单机对象、无超时、答完消失。**借它的展示形状可以（前端的事），借它的状态不行。**

### 3-6（不吸收）Source 轮询 + Disposition

它解决的是"自动拉取外部源、按位点消费"。我们 v1.0 是**人工触发回读**（飞书 MANUAL），没有常驻轮询；等真做自动拉取再回来看。

## 4. 最终结论（回答"哪个是最优解"）

**分三层，各层的最优解不同，不能混着选：**

| 层 | 最优解 | 一句话理由 |
|---|---|---|
| 真相层 | **自建 PG（现状）** | 只有它同时满足"跨进程 + 可审计 + 可追责"；另两家的真相是会话日志/单机 SQLite |
| 执行载体 | **DSH（现状）** | 会话、审批、计量、子进程——自研就是重复造 Runtime（R1） |
| 设计形状 | **prototype，只借 3 个点** | 效应先存后做（暂不启用）、人工槽位、recovery note；领域模型和 Attention 不借 |

**所以"要不要更吸收超级架构"的答案是：不整体吸收，只吸收上面两条半。** 因为它的强项（先存后做）我们还没有使用场景，它的弱项（单机、重启判死）正好踩我们的产品底线。

**真正该做的三件（按性价比）**：
1. **engine 层定性**（退役 / 拆到未启用）——最便宜的清理，去掉"装了没人喂"的歧义；
2. **人的槽位优先**——批量时 HR 的操作不排队；
3. **recovery note**——重开时知道上次做到哪。

前两件各是几十行；第三件是任务书里加一段。**都不动架构、不动前端、不动产品口径。**
