# 设计理由（为什么这样做）

**日期**：2026-11-13
**性质**：这不是需求文档，是**决策记录**——每个设计选择背后的理由、被否掉的方案、以及踩过的坑。
**为什么要有它**：同一个坑我们已经踩过两次（详见 §7）。不写下来，下一个人会重新踩。

---

## 1. 为什么基于 DSH，而不是继续自研

**背景**：上一轮项目自研了一套 `apps/api + apps/web + apps/worker + packages/*`，5.2 万行。结果是 40% 的模块该被替换却被自研，最终路线废弃。

**判断**：招聘系统真正难的是**领域规则**（状态机、不变量、证据链），不是**基础设施**（会话、工具调度、UI、定时、审批）。后者 DSH 已经做了（279,068★，开源）。

**结论**：
- 底座 = DSH（Web 版；桌面与 Web 只是 UI 面不同，内核一致）
- 我们只写：招聘语义 + 工具 + 校验 + 兜底
- **不 fork DSH 源码**；加减都走 profile 的 bundle/patch 层（DSH 原生支持按 id 禁用）

**代价与边界**：DSH 提供的部分我们不改；需要改内核时必须先论证"插件机制做不到"。

## 2. 转换层（简历文件 → 文本）为什么是四件套

**问题**：PDF 千奇百怪（纯文字、文字+图片、扫描件、加密、损坏、非嵌入中文字体）。任何单一手段都会漏。

**四件套的分工**：

| 件 | 职责 | 为什么不能省 |
|---|---|---|
| **工具层** | PyMuPDF 读原生文字 + 坐标 | 唯一能提供**坐标证据**的来源 |
| **校验机制** | 独立校验器按 doc 11 判合格 | 转换器自己说合格不算数（实现者不能验收自己） |
| **模型兜底** | 读不出的页 → 渲染成图 → 模型读 | 工具读不了的东西，模型可能读得了 |
| **人工兜底** | 人读、人录入、并存 | 机器和模型都读不了时的最后一层 |

**关键设计**：
- **校验器必须独立于转换器实现**（只读输出 JSON + 用 fitz 自己重读原件），否则就是自己验自己
- **模型兜底的核心不是"让模型读"，是"读完必须被拦"**：空字符串、拒绝话术、与原生文本无关（重叠率过低）→ 一律不合并
- **人工兜底的核心不是"入队"，是"阻断"**：队列里未处理的项，下游必须拒绝出结论，不能静默跳过

**已知边界**：扫描件不 OCR 造正文（会丢正确内容）；版面几何后端未配置时，阅读顺序只能发现不能修正。

## 3. 文本 → 结构化：为什么必须先"带 id 序列化"

**被否掉的方案**：直接把纯文本丢给模型，让它返回结构化结果。

**为什么不行**：模型说"电话是 13812341234"，如果没有编号，你**无法核对**它是不是编的。

**采用的方案**：

```
文本块（有坐标）
   ↓ 序列化 = 给每段贴编号：#12 | p1 | 工作经历
带编号的文本
   ↓ 模型结构化（只能引用 #12）
结构化结果
   ↓ 机械校验（值必须是引用块原文的子串）
通过 / 打回
```

**编号不是额外阶段，是校验的前提。** 没有编号，幻觉拦不住。

**三个配套设计**：
1. **输入必须带 `#doc` 文档头**（页数、完整性、**顺序是否可信**）。理由：阅读顺序不可信这个事实不在 issues 里而在 `meta.order_verified=false`，模型看不到就会在顺序不可信的文档上**合法地写 absent**
2. **覆盖率检查**：每个块必须**恰好归入一个 section**，漏了就是漏读
3. **降级链**：模型不可用 → `unreadable` + 人工，**不崩不猜**

## 4. 为什么放弃"词表拟合"

**被否掉的方案**：用章节关键词（工作经历/教育背景/项目经历…）切分简历。

**实测数据**：45 份新简历里，`work_experience` unreadable **42%**、`education` unreadable **53%**。原因是词表太窄（「实习经历」「科研经历」「Professional Experience」都不在表里）。

**结论**：词表是最脆的办法。正确顺序是**版式优先、语义兜底**：
- 版式信号（字号跳变/字重/行长/留白）找标题 → 不依赖任何词
- 词表只用来**贴标签**，不用来找标题 → 词表不中最多是 `unknown`，不会丢掉整节内容

**两次教训**：我连续两次试图用规则拟合自然语言（章节词表、姓名归一化），两次都被真实数据否掉。**规则适合做机械校验，不适合做语义理解。**

## 5. 字段三态为什么是硬约束

**三态**：`present` / `absent` / `unreadable`

**为什么不能二态**：
- `absent` 的语义是"原文确实没提"
- `unreadable` 的语义是"有，但读不出来"
- **把 unreadable 当 absent，系统就会理直气壮地淘汰一个其实符合条件的候选人**，而且事后无法解释

**落地**：
- 任何 issue 或 `needs_visual` → `completeness` 强制降 `partial`
- 筛选时：`unreadable` **绝不能**当作"不满足"，只能产生"待人工确认"
- 工作年限：下界够 → SATISFIED；下界不够 → **INDETERMINATE**（绝不 UNSATISFIED）

## 6. 为什么 v1.0 不做权限

**决策**：不做 RBAC，所有人**全局可见**；但每人有"个人工作台"（按"分配给我的"过滤）。

**理由**：
- v1.0 的目标是跑通业务链，不是做企业级安全
- 6 角色 × 资源 × 动作的矩阵会把开发时间吃掉，而它对"跑通"没有帮助
- 角色**降级为标签**，只用于工作台过滤和界面展示，**不用于拦截**

**明确不做**：不写永远返回 true 的 `can()` 假接口——那种东西比没有更糟。

**将来要开权限时必须补**：数据范围判定、工具级检查、审计。

## 7. 我踩过的两个坑（必须记住）

### 坑 1：把罕见情况做成闸门

**我做的**：为"同手机号不同姓名"设计了人工闸门，还编了"家庭共用手机号 / 父母代投 / 猎头转发"三个场景来论证。

**纠正**：真实招聘场景里**简历上的姓名就是候选人本人**——HR 不会用别人名字，候选人不会不填自己名字，猎头转发的也是候选人自己的简历。**那三个场景不成立。**

**教训**：设计前先问"这在我们这里会发生吗、多大概率"。**把罕见情况做成闸门，会让 99% 的正常简历承担成本。**

### 坑 2：把"看起来像问题"的当成问题

**我做的**：列了 `张三 / 张 三 / 张三(Zhang San) / 全半角 / 曾用名` 五种"高概率"姓名差异，还说要检测手机号填错（少一位多一位）。

**纠正**：只有前两种可能，而且**模型结构化时不会搞错**；手机号填错不关我们的事。

**教训**：**先确认这是不是我们的问题，再决定要不要设计。**

## 10. 给下一个人的话

1. **先读 `work/decisions/`**，那里每条裁定都有理由，不要重新发明
2. **不要相信"测试全绿"**：要看 `passed / failed / skipped` 三个数，`skipped > 0` 不算绿
3. **未接线 = BLOCKED**，不是"完成"
4. **实现者不能验收自己**：自己写的代码要有独立证据
5. **设计前先问"这在真实场景会发生吗"**，不要凭想象堆防御
