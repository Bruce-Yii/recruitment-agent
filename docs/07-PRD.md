## 1. 产品定义

**一句话**：面向企业招聘全生命周期的 Agent-native Recruitment Operating System——用户通过自然语言或结构化工作台提出招聘目标，Agent 理解企业与招聘上下文，动态组织工具、Worker 和工作流，持续推进需求、岗位、人才获取、筛选、面试、评价、决策、Offer 与入职交接；系统自动处理可自动化的事务，**人只在必要的判断、审批和异常处介入**。

**产品不是什么**（X）：
- 只做简历解析/管理/筛选的单点工具
- 传统 ATS 页面里加一个聊天机器人
- 让 HR 逐个点击、上传、复制、催办的工具集合
- 多个平等 Agent 自由通信、相互派活的 Agent 群
- 重建 HRIS / 企业知识库 / 邮箱 / 日历 / 会议系统
- **由模型独立决定淘汰、录用或 Offer 的自动决策系统**
- 面向求职者的公共招聘平台或候选人门户

**核心差异**：传统系统要求人理解模块与固定流程再逐步推动；本系统要求**系统理解人的工作目标**，由 Agent 在运行时组织完成工作（`Observe → Understand → Plan → Act → Verify → Replan`）。

## 2. 产品目标与成功衡量

### 2.1 七个产品目标
完整招聘闭环 · 减少事务性工作 · 自然语言驱动 · 后台持续执行 · 保留人的判断权 · 证据与过程可追溯 · 持续学习与优化。

### 2.2 价值验证方向（不预设未测量的基线）
先验证是否真正减少**人工接力、信息搬运、被动等待**：
- 可避免人工交接与重复操作是否减少
- HR / 面试官实际处理时间是否减少
- 因等待人员/资料/外部系统/内部处理造成的阻塞是否减少
- **Agent 输出是否真正进入业务工作流，修改与拒绝的原因是什么**
- 招聘质量、证据完整性与关键决策是否仍可靠

### 2.3 三项核心效率指标
`Avoidable Manual Touches` / `Active Human Handling Time` / `Blocked-Waiting Time`
> 均从底层业务事实推导；**不预设降幅目标**；**Active Human Handling Time 无可靠起止记录时不计算**；**不拿页面停留冒充人工处理时间**；样本不足时显示样本量与不确定性。

## 3. 用户与角色

| 角色 | 主要目标 | 主要操作与责任 | 优先级 |
|---|---|---|---|
| 企业管理员 | 系统在企业环境中可用且受控 | 组织、用户、角色、连接器、全局政策、数据访问范围 | P0（最小） |
| 招聘负责人 / HR 主管 | 管理招聘目标、标准与结果 | 确认岗位标准、审核流程、审批、看进展、授权范围内正式决策 | P0 |
| HR / 招聘专员 | 高效推进招聘执行 | 接简历、处理候选人、看初筛结果、排期、沟通、跟进、处理异常 | P0（首要用户） |
| Hiring Manager | 找到符合业务目标的人 | 提需求、参与岗位校准、确认能力标准、面试与用人决策 | P0 |
| 面试官 | 高质量完成指定轮次面试 | 看授权上下文、准备问题、面试、看转写证据、独立提交 Scorecard | P0 |
| 审批人 | 对明确事项作正式批准 | 审批/退回/拒绝并留理由与时间 | P1 |
| **候选人** | — | **外部参与者，不是本产品工作台用户**；系统支持流程所需的通知/资料接入/状态交互，但不建候选人门户 | 边界 |

**角色设计要求**：入口与可见信息围绕**真实工作职责**设计；**不先做复杂权限矩阵再倒推体验**；但**服务端必须保证角色、资源范围与授权边界**。

### 4.7 FR-N 面试与材料（阶段 8–9）

| ID | 需求 | 优先级 | 验收要点 | 归属 |
|---|---|---|---|---|
| FR-N1 | 创建 Interview，指派**至少两位**面试官，建立 Meeting Binding | **P0** | 绑定用真实 provider 标识，**不靠标题猜** | W5+W6 |
| FR-N2 | 按真实约束（候选人/面试官可用、时区、时长、轮次间隔、企业工时）提排期 | **P0** | **会议室不是默认约束** | W5+W6 |
| FR-N3 | 创建/确认/改期/取消/冲突处理；改期后**旧 Meeting 转写不与新 Meeting 拼接** | **P0** | 断线续接不靠时间接近认定 | W5+W6 |
| FR-N4 | 面试前自动备料：JD/Rubric、简历要点、前序客观摘要、本轮 Focus Attributes、问题建议 | **P0** | **不要求面试官手动整理已能取得的东西** | W5+W4 |
| FR-N5 | 会后自动获取**全部**转写产物与**全部分页**，保存原文 + artifact ID/revision/hash/完整性元数据 | **P0（真实飞书）** | 见 §4.8 保真规则 | W6+W5+W3 |
| FR-N6 | 归一化 Segment：说话人/时间戳**平台没给就留空 + 稳定 locator** | **P0** | **不编造、不推测补齐** | W5 |
| FR-N7 | Chunk Manifest（约 3k–5k tokens/块、留 1–2 轮次重叠、按 Segment ID 去重）+ 分块提取 + Validator 校验证据与覆盖 | **P0** | **全成功才 READY；部分失败只重试失败块** | W5+W3 |
| FR-N8 | Interview Record 八区块（Overview / Neutral Summary / Q&A / Evidence by Competency / Covered / Unclear-Unverified / Follow-up / Source Refs） | **P0** | **不打分、不下录用结论、不把自述写成已验证事实** | W5 |

**FR-N5 的七条保真规则**（缺一不可）：
1. 事件只是触发信号，不是"已取到"
2. **完整性 = 平台实际返回的产物与分页是否取全**，不是要求平台提供它没有的数据
3. **平台没给的字段保持缺失**，不用内部推测值伪装外部事实
4. 只拿到部分 → `PARTIAL`，**绝不 READY**
5. 不静默覆盖原文；不静默拼接多 Artifact
6. 授权失效 → `AUTH_REQUIRED`，**绝不降级 Fixture 却显示 LIVE**
7. 绑定歧义 → `NEEDS_LINKING` 交人工，**不猜**

## 5. 非功能需求（NFR）

> **范围声明**：本节的「数据治理」部分是**最小工程基线**，不是特定司法辖区的合规认证，也不是生产级安全计划（`docs/09` 状态行原文：*"Minimum engineering baseline approved for local-first Demo. This is not a jurisdiction-specific legal compliance certification or a production security program."*）。Notion 12 页对应节标题为「隐私、权限与数据生命周期」，其中「隐私合规系统的重新实现」被明确列为**不做**。

| ID | 类别 | 要求 |
|---|---|---|
| NFR-1 | **正确性** | 关键候选人信息、筛选依据、面试事实必须有来源；AI 推断不能伪装成候选人明确提供的事实；原始简历/原始转写/人工 Scorecard/正式 Decision 不能互相覆盖 |
| NFR-2 | **自动化可靠性** | 重复事件不重复创建候选人/申请/外部副作用；部分失败不伪装成整批完成；授权失效/转写未生成/日历冲突/发送未知时保留明确状态与恢复入口；可恢复任务不要求用户重述全部上下文 |
| NFR-3 | **并发** | 业务聚合用 `expected_record_version` 条件更新；冲突返回 `VERSION_CONFLICT`；不引入分布式锁；Worker 用 `fencing_token` 防过期提交 |
| NFR-4 | **幂等** | 四层独立：事件去重 / Task 创建 / Attempt 重试 / Effect + 外部回执；**不宣称全局 Exactly-once** |
| NFR-5 | **安全** | 服务端 `Actor × Tenant × Role+permission_version × Resource Scope × Action × Mandate`；**工具每次执行重校验**；**不依赖 Prompt** |
| NFR-6 | **不可信输入** | 简历/邮件/附件/公开主页/会议转写**始终作为不可信数据**；其中的指令不得提升权限；默认禁止任意 Shell/文件/网络 |
| NFR-7 | **数据治理与个人信息处理** | Demo 默认合成数据；真实简历/转写仅在明确获准且必要时进入；原文放受控存储，**普通日志只保留 ID/引用/摘要，不复制整份简历或转写**；不记录密钥/Token；不默认用于模型训练；明确处理目的、访问范围、保留期限与删除/更正路径；**不设统一保留天数**（按企业政策与适用辖区确定） |
| NFR-8 | **公平性** | 不以受保护特征或其明显代理变量筛选；无证据结论须标未知/待核实；**不以单一 AI 分数作为自动淘汰唯一依据**；偏差监测须有合法用途与数据隔离，**不把受保护特征写进普通候选人画像** |
| NFR-9 | **可观测** | 以 `correlation_id` 串起 Event→Task→Attempt→Session→ToolCall→Effect→Receipt→业务状态；**不做全量点击埋点** |
| NFR-10 | **本地可运行** | 本地 Web/API/Worker + PostgreSQL + pg-boss；clean checkout 可安装、迁移、seed、跑通 Golden Path，**无需手工改库** |
| NFR-11 | **可移植** | Agent Runtime 通过产品自有 Adapter 抽象；不绑定单一 Runtime 的实现细节 |
| NFR-12 | **数据生命周期** | 明确处理目的、访问范围、保留期限、删除/更正路径；删除时考虑原文文件、派生摘要、索引、缓存；**不设统一保留天数** |

## 7. 验收标准

### 7.1 产品级八条
1. 用户目标可完成 2. 业务结果真实落地 3. 自动化符合预期 4. 证据与版本完整 5. 人工职责正确 6. 异常可处理 7. **外部能力诚实** 8. **前序版本不回归**

> 逐字：**"每项功能不能只以'页面存在''模型回复成功'或'Agent 自报完成'作为验收。"**

### 7.2 证据规则 E1–E4
`E1` 端到端可达（运行入口→事实，含命令/真实输出/DB 读回）· `E2` skip 计入（`passed/failed/skipped` 三数，`skipped>0` 禁称全绿）· `E3` 被引用证据必须存在（CI 检查）· `E4` 未接线不得通过（不可达即 `BLOCKED`）。

### 7.3 Demo Gate（v1.0）
- 本地从 clean checkout 可复现安装/迁移/seed/启动
- 全 Golden Path **无需手工改库**
- **转写段使用真实飞书产物，标 `LIVE` + provider `FEISHU`**（或明确标注的 `MANUAL` 真实拉取）
- 测试覆盖域不变量、运行时契约、关键恢复路径
- 无遗留 P0 授权/数据完整性/重复副作用问题
- demo 脚本标明 live / fixture / manual 路径
- **集成者独立读回任务状态、域记录、测试输出、外部回执**
