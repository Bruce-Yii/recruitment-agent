# 11 · PDF 转换器验收标准

**日期**：2026-11-12
**适用范围**：招聘 Agent 系统的 PDF 读取器（DSH 工具形态）
**对齐**：`resume-conversion-build` 的 `documents.read_pdf()` 判定顺序 + `content.py` 契约 + 本项目 E1–E4 / R3 / R4

---

## 0. 一句话标准

> **验收的不是"能抽出多少字"，而是"抽出来的每个字都有出处，抽不出来的每一处都有说明"。**

字符数、自动率、非空——**都不是验收证据**。它们只能证明程序跑过，不能证明读对。

---

## 1. 输出契约（先定形状，再谈对错）

```json
{
  "text": "...",
  "blocks": [{ "kind": "paragraph|link|heading",
               "text": "...",
               "location": { "page": 3, "bbox": [x0,y0,x1,y1] },
               "links": [{ "text": "...", "href": "https://...", "location": {...} }],
               "provenance": "native_text|ocr_title|agent_read" }],
  "completeness": "complete|partial|unverified",
  "issues": [{ "code": "...", "message": "...", "location": {...} }],
  "needs_visual": false,
  "warnings": [],
  "meta": { "pages": 11, "source_sha256": "...", "backend": "pymupdf+layout/1.28.0" }
}
```

**硬性**：任何 `issue` 或 `needs_visual=true` → `completeness` 必须降为 `partial`。
**未知 issue code 一律按 HARD 处理**（保守优先，抄 `batch.py:130`）。

---

## 2. 六个维度与判据

### A. 保真（最重要）

| # | 判据 | 机检方式 |
|---|---|---|
| A1 | **页覆盖完整**：输出页集合 == 原生页集合；每页要么有 block，要么有 issue | 比对页号 |
| A2 | **字符不增不减**：逐页 `Counter(非空白字符)` 完全相等 | `Counter` 比对（已有实现） |
| A3 | **不改写**：正文不得含工具生成的解释/摘要/修正；不做毯式 NFKC | 关键词扫描 + 人读 |
| A4 | **顺序可信**：有版面后端按几何；无后端时若内容流回跳——页字 <800 必须 HARD，≥800 可降 warning | 复用 `stream_order_issue()` |
| A5 | **链接不猜**：`get_links()` 的真实 URI 全部出现；**凭空 URI 必须为 0**；链接与所属块绑定 | URI 集合比对 |
| A6 | **坏字形不进正文**：出现 `\ufffd` / `(cid:N)` / 控制字符 → 必须 `pdf_text_encoding_unread`，且这些字符不得出现在正文 | 正则扫描 |

### B. 诚实（读不到要说）

| # | 判据 |
|---|---|
| B1 | 页字符 <80 且有图形 → `unread_visual_page`；全文无 block → `pdf_no_text` + `needs_visual` |
| B2 | 加密且无空密码 → `encrypted_pdf`，不得崩 |
| B3 | **不可静默**：任何"读不到/只读了一部分"必须出现在 issues，并触发 completeness 降级 |

### C. 稳定（可重复）

| # | 判据 |
|---|---|
| C1 | 幂等：同输入两次运行，输出 byte-identical（除时间戳/绝对路径） |
| C2 | 原件不变：读取前后 SHA256 相同 |
| C3 | 超时：单份 ≤50s；超时 → issue，不挂死、不产生半截正文当成功 |

### D. 下游可用（招聘系统特有）

| # | 判据 |
|---|---|
| D1 | 每条结构化字段（姓名/电话/邮箱/公司/时间）必须能回指到 block 的 `page + bbox` |
| D2 | `provenance` 必须逐块标注：`native_text` / `ocr_title` / `agent_read`；**不得混标** |
| D3 | 来自 `ocr_title` 或 `agent_read` 的**身份类字段（姓名/电话/邮箱）不得用于自动候选人合并**，只能进人工复核 |

## 3. 分层通过门槛（按载体分，不按文件名）

| 层 | 通过门槛 |
|---|---|
| **纯文字 PDF**（中/英） | A 全过，HARD issue = 0 |
| **双栏/复杂版式** | A 全过；顺序不可信时必须 HARD，不得当作已读 |
| **矢量标题型**（标题不是文本） | 正文 A 全过；标题缺失必须记录，**不得编造标题** |
| **扫描/图像型** | **必须 100% 正确识别为图像型**（B1）；正文允许缺失，但**不得伪造** |
| **加密 / 损坏** | 必须报对应 code；不得崩溃、不得静默返回空 |
| **超大（>50 页）** | 不得截断正文；超时必须报 issue |

> 关键：**图像型的验收点是"识别对不对"，不是"能不能读出字"。** 把扫描件读成"空简历"是最严重的错。

---

## 4. 怎么测才算数

1. **样本分层**：每层 ≥10 份**真实简历**（不用合成件），总样本 ≥60 份。
2. **双轨报告**：
   - 机检（上表 A–D）→ 报通过/失败数
   - 人工读原件对照 → 随机抽 ≥20%，且**所有 HARD issue 必读**
3. **禁止**：
   - 用字符数 / 非空 / 自动率当质量证明
   - 用"生成成功"当"读对了"
   - 只跑机检就宣布通过

---

## 5. 红线（出现即不通过）

1. **静默丢页/丢块**（无 issue）
2. **输出原生不存在的文字**
3. **扫描件返回空文本却标 `complete`**
4. **同输入两次结果不同**
5. **崩溃或挂死**
6. **用 OCR 正文替换原生正文**（历史决定：整页覆盖会丢正确正文）

---

## 6. 与项目规则的对接

| 规则 | 在转换器上的落法 |
|---|---|
| E1 端到端可达 | 从 DSH 工具入口真实调用，给出命令 + 真实输出 + 文件读回 |
| E2 三数 | 报 `passed / failed / skipped`；`skipped > 0` 不得宣称全绿 |
| E3 引用可查 | 每条 PASS 引用的样本文件必须真实存在 |
| E4 未接线 = BLOCKED | 未配置版面后端时，顺序问题不得记为"已解决" |
| R4 三维标签 | `provenance`（native/ocr_title/agent_read）× `trigger` × `connection` 分开标 |
| R3 证据 | 机检 + 人读分开报告，不得混为一谈 |

## 7. 我认为最容易做错的两点

**① 把"字符多"当"读得对"。**
实测：同一份 11 页英文简历，pdfjs 抽出 16,950 字符，PyMuPDF 抽出 16,226 字符。**差 724 字符必须逐条解释**（是重复块、页眉页脚、还是 UI 噪声？）。解释不了，就不能算保真——只能算"跑通了"。

**② 把"自动率"当"质量"。**
转换层自己的结论就是"生成率不是质量合格率"：1020 份 MD 里 375 AUTO / 644 PARTIAL，正常机械 80% **未证实**。我们如果重复这个错，就会再走一遍"16/16 PASS 但 DR 0/8"的老路。

## 8. 当前可实现性

上表 A1/A2/A5/A6/B1/B2 的判据，`resume-conversion-build` 的 `read_pdf()` **已经实现**（`Counter` 校验、链接中心点归属、issue code、`stream_order_issue`）。
所以这套标准不是空想——**是对齐一份已经在跑的实现的**。我们要补的是 A3/A4 的后端配置、C1 幂等测试、D1–D3 的证据回链。

## 9. 招聘 Agent 特有验收（通用转换器没有的）

> 通用转换器的红线是「**读错了**」；
> 招聘 Agent 的红线是「**读错了还拿它做了对人的决定**」。

### 9.1 归属正确性（最致命）

简历里"公司—职位—起止时间"常跨行、跨栏、跨块。错行 = 经历张冠李戴，直接影响筛选结论。

**判据**：每条经历的（公司 / 职位 / 起止）必须来自**同一区块**且坐标连续；跨区块拼装必须报 issue，**不得静默组合**。
**测法**：构造"公司A—职位B"跨栏样本，验证系统报 issue 而不是给出错误归属。

### 9.2 字段三态：present / absent / unreadable

简历没写某项，和"写了解析不出"是两件事。

**判据**：每个字段必须落在三态之一——
- `present`：原文有且已读出
- `absent`：原文确实没有提及
- `unreadable`：原文有但读不出

**红线**：`unreadable` 绝不能当 `absent`。下游筛选必须能区分。

### 9.3 拒绝可解释

**判据**：任何"不符合"的判定必须携带该字段的三态 + 证据坐标。
**红线**：因读取失败而淘汰候选人 = 不通过（这是比丢字更严重的错误）。

### 9.4 时间线可解析且不得自动修补

**判据**：`2020.07-2023.06` / `2020年7月至今` / `Jul 2020 – Jun 2023` 等格式可归一为可比区间；解析不出的时间必须暴露；**断档、重叠、倒挂必须报 issue，不得自动补齐或猜测**。工作年限由时间线**可复算**得出，不得由模型估算。

### 9.5 平台噪声排除

招聘网站导出的 PDF 常带页眉页脚水印（BOSS直聘 / 猎聘 / 智联）、二维码、平台广告。

**判据**：必须识别为噪声并排除出正文，**且排除要有记录**（否则可能把平台名误当公司名）。这是招聘 PDF 独有的坑。

### 9.6 受保护属性隔离

年龄、性别、婚育、籍贯、民族、照片。

**判据**：必须能识别并**隔离**，**不得进入筛选特征**。理由不是"隐私合规口号"，而是产品正确性——否则会做出歧视性筛选，且无法申诉。

### 9.7 身份字段不得驱动自动合并

**判据**：
- 来自 `ocr_title` / `agent_read` 的姓名/电话/邮箱 → **只能进人工复核**，不得自动合并候选人
- 仅 `native_text` + 格式校验通过才可自动匹配
- 自动合并必须记录"依据了哪些字段"

### 9.8 多版本冲突显式化

同一人投递多份、中英双版、不同岗位版本。

**判据**：冲突（不同公司/不同时间/不同职位）必须显式记录并按既定规则择一（中文优先 / 最新优先）；**不得静默合并成一份"完美简历"**。

### 9.9 决策可回溯

**判据**：每条结构化事实 → `page + bbox + 原件 SHA256`。HR 复核、候选人申诉、内部审计都要能回答"当时看到的是哪一版、哪一行"。

### 9.10 批处理隔离与幂等

**判据**：单份失败不污染整批；可续跑；同输入重跑结果一致；失败清单必须给出原因 code（不是"失败了"三个字）。

### 9.11 招聘特有红线（追加到 §5）

7. **把 `unreadable` 当 `absent`，并据此淘汰候选人**
8. **跨区块拼装经历（公司/职位/时间错配）**
9. **受保护属性进入筛选特征**
10. **OCR/Agent 来源的身份字段触发自动合并**
