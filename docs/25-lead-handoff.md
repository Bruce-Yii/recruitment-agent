# 25 · 总控交接（2026-11-17 · 给下一位 lead）

> **这份文件不教你怎么跑测试。** 测试、全量、CI 红绿是**最低标准**——任何窗口都能做，做到零红也不代表项目对。
> 这份文件要让你接住三件东西：**这个产品是什么、为什么这么设计、下一步该往哪走**。判断力在这三件上，不在别处。
> 产品认知与验收口径的唯一权威 = **`docs/24-product-framework-v2.md`**；裁决的唯一权威 = **`docs/17-decision-ledger.md`**。

---

## 0. 一句话

**我们做的是跑在 DSH 上的"招聘 Agent"：以「人」为单位把散落的上下文串起来，用 Agent 把它结构化、标注、给建议；判断权永远在人手里；外部世界只"接进来"，不接管。**

不是招聘平台，不是人事系统，不是沟通工具，不是流程引擎。

---

## 1. 产品为什么长这样（先理解"为什么"，再谈"做什么"）

### 1.1 真实招聘的痛点不是"缺系统"，是"上下文散落"
候选人的情况散在简历里、面试官脑子里、飞书聊天里、HR 的 Excel 里；招一个人要问一圈人、翻一堆文件。
→ 所以我们的第一性不是"建流程"，而是**把人身上的上下文攒起来并让它可读**。

### 1.2 所以数据以"人"为单位，不以"阶段/模块"为单位
一个人的简历、每一轮面试、面评、决策、结果，全挂在**这个人这次申请**上。
阶段（S6 收简历 / S7 初筛 / S8 面试 / S9 转写 / S10 决策）只是**业务标签**，不是模块清单，也不是进度指标。
→ 推论：**不需要**"人才沉淀模块"（数据本来就在）、**不需要**"角色×视图矩阵"（按"这一轮需要什么上下文"给）。

### 1.3 Agent 是辅助，不是替代
它做三件事：**读上下文 → 结构化/标注 → 给建议**。
它**不**替人做初筛结论、**不**替人决策、**不**替面试官打分、**不**替企业发 Offer。
→ 推论：任何"让 Agent 替人拍板"的设计都是错的；任何"让人去做本不该他做、或系统该自己做的事"的设计也都是错的（例：让 HR 去定面试官的问题）。

### 1.4 人的判断必须留在人手里，且留痕
批准评分标准、交面评、做决策——必须真人、在真实界面、写进库、可追责（谁、何时、依据哪份材料、哪版标准）。

### 1.5 外部世界只"接进来"
企业人事系统、飞书日程/会议/转写、投递渠道、公开信息 —— 这些是**外部**。我们只定义**通用连接器契约**，不实现具体客户对接；**不在系统内做沟通协调**（拉人开会、站内催办）。沟通在系统外发生，我们记录结果。

### 1.6 复用优先，不自研
底座是 **DSH**（会话、子代理、任务面板、token/上下文计量、skill、preset 全是现成的）+ **PostgreSQL**（业务真相）。
**自研队列/Runtime/解析/UI 框架 = 违规**。我们只写"招聘语义 + 胶水 + 展示"。

### 1.7 五个事实分离（架构的骨架）
**业务事实**（PG 里的领域表）· **事件**（发生了什么）· **任务**（要做什么）· **执行**（谁在跑、跑了几次）· **副作用**（对外做了什么、回执是什么）。
→ 推论：Agent 不拥有不变量；任务真相在 PG 不在会话里；长任务必须跨会话可恢复；外部副作用必须有回执。

## 2. 当前方向与阶段

- **v1.0 = 一条纵向切片**：简历进来 → 读得懂 → 人看得明白 → 面得下去 → 评得出来 → 人做决定 → 事后查得到。**只证明三件事**：业务真相归领域、长任务跨会话、外部事实诚实。
- **现在处于"让这条切片真的能用"的修复与打磨期**：上一轮独立验收判过 **产品/业务 FAIL**（Agent 靠 shell/psql 读业务事实、记录人的决定退化成读源码算哈希、姓名解析错、rubric 判断不了 JD、成本失控）。这一轮把 20 条 `OURS` 修完了（见 §4），正在补"HR 真的能感知到"的最后一层。
- **模型口径**：本阶段是**本地开发/验证**，统一用免费 **HY4**（`hy4-flash-free`）。**别拿"交付质量"反对**——交付口径另立裁决，现在不是交付。
- **UI 状态**：工作台设计**未定稿**，所以 UI 布局/视觉**冻结不修**（D-135）；但**文案、数据一致性、错误可读性**必须修。

## 3. 判断框架（这是你要带来的唯一真本事）

### 3.1 任何问题按三层顺序答
1. **业务**：这个动作真实由谁做？**是他的职权吗**？
2. **产品**：HR/面试官**会感觉到什么变化**？（答不出来的改动，优先级最低）
3. **工程**：怎么实现、怎么证明。

### 3.2 设计任何流程前，先答四问
**谁做？是他的职权吗？谁受益？会不会要求人越出角色？** 答不上来 → 不许写进产品流程（可以写进"不主动提"或"待设计"）。

### 3.3 真问题 vs 伪需求
| 真问题（要做） | 伪需求（别做） |
|---|---|
| 决定"通过"还要再点一次推阶段；决定"不通过"还挂在"在办" | 退回补充材料状态机（简历就一份，收到什么就是什么） |
| 材料只能引用字段，核不到原文 | 让 HR 在系统里定面试问题 |
| 面试官不知道上一轮问了什么 | 多面试官联合会审、分歧仲裁 |
| 已拒申请被显示"去安排面试" | 独立"人才沉淀"模块 |
| 按岗位名/候选人名找不到对象 | 主动捞人 sourcing |
| 系统内部编号被念给 HR | 角色×视图矩阵 |

### 3.4 三句话概括产品口径
- **收到什么就是什么**：不判定"缺件"、不索要材料、不要求人补录系统没读出来的字段。
- **流程是线性的**：一面依赖初筛，二面依赖一面；不做并行会审。
- **参考不是指令**：Agent 给"这一轮可以了解什么"，怎么问是面试官职权。

## 4. 已经做出来的东西（产品语言，别再重做）

**HR/面试官能感觉到的**
- 初筛"通过/不通过"**一次点完**：通过自动进下一阶段；不通过这条申请**自动结束**，工作台不再催你安排面试。
- 材料能引用到**"第几页第几行"**的原文，面试官能核对，不用自己翻 PDF。
- 面试官打开一场面试，能看到**紧邻上一轮实际发生了什么**（按岗位标准：覆盖了哪些、哪些没覆盖、面评结论），以及**这一轮可以参考的 4 条要点及理由**。
- 按**岗位编码/标题**、按**候选人姓名**都能找到对象，不用记 UUID。
- 工作台里不再出现机器码/接口路径/"缺件"这类工程话；转写没到就说"还没有转写"。
- 决定可追责：谁、何时、依据哪份材料、哪版标准，库里查得到（`tool_call` 留痕也补上了）。

**Agent 能力**
- 30 个工具（29 个 `recruitment_*` + 高层 `record_human_decision`），Web 会话工具面收口到 **36 个（工程工具 0，不是被拒，是注册表里就没有）**；会话跑产品自有 preset「招聘助手」，不再自称 coding agent。
- 高层"记录人已做的决定"：服务端组装依据与哈希，Agent 只传业务语义；事件带四个确认审计键。
- 姓名解析只认可信来源（标签/h1），读不出就如实 `absent`，不猜。
- rubric 质量门槛：判断不了 JD 时给 `QUALITY_WARNING`（advisory，不改 verdict、不写库、不自动改标准）。
- 五个环节「工作说明书」骨架（S6–S10），纪律写死：输出三段式、**禁止反向免责话术**、不索要材料、不暴露内部标识。

**基础设施**
- 长任务跨会话可恢复（kill 后同 task 续跑、attempt 递增）；真实飞书转写一条真链（LIVE/MANUAL/CONNECTED、哈希可对）。
- 材料读取支持 PDF/DOCX/RTF/纯文本，证据按 D-110"可复核"判定（源哈希一致 + 定位唯一 + 原句逐字命中），**不再因缺坐标判"读不出来"**。
- 只读展示端点：原件受控获取（不暴露路径）、DSH 会话计量（token/缓存/上下文，原样透出）、任务与卡住事件状态。

## 6. 我踩过的判断类错误（反面教材，务必别重复）

1. **用"能实现"代替"真实业务谁负责"**。我设计过"HR 给面试官定面试重点""多面试官分歧仲裁""缺件让 HR 补""时间协调做到系统里"——全是凭想象造场景。
2. **把线性流程说成并行会审**。招聘逐轮推进，不是多方会审。
3. **把工程正确性当产品进度**。花大量时间在追溯环、机检、测试数——HR 看不见。**汇报先说"用户会感觉到什么"**。
4. **在开发环境用"交付质量"当理由**。我拿"HR 体验"反对在开发环境用免费模型，被骂。**先分清阶段**。
5. **把"缺口"做成焦虑清单**。给面试官列"这块没问那块没问"是错的；只列岗位标准内的维度，且是事实陈述。
6. **替产品负责人做决定**。产品语义变更必须写成裁决（例：REJECT = 申请结束，这条我裁了并入了台账）。
7. **"不做清单"写太死**。正确是"**不主动提**"：不主动扩范围、不塞进验收；明确要求时可做，但要先说代价 + 立裁决。
8. **声称"已派"而实际没派**（诚信红线）。**先调工具，再写"已派"**；进度必须给得出产物路径或 agent 名。

工程侧只有少数坑值得记（其余看 `docs/17` 与各 REPORT）：
`--dump-config` 通过 ≠ 运行时生效（Web 会话工具面由 preset 子树决定）；profile 改完要同步到 `DSH_HOME/profiles`；测试库与产品验证库必须分开（否则种子被污染假红）；`ctx.effect(fn)` 会立刻执行 fn（别把 dispose 直接传进去）；profile 新增行要用 `insert` 语法。

## 9. 接手后先建立这三个认知（不是先跑测试）

1. **产品要什么**：用一句话说清"我们做的是招聘 Agent，不是招聘系统"，并举例说明哪些"看起来该有"的东西我们**故意不做**。
2. **现在到哪**：哪些能力已经能用（HR 能感觉到）、哪些是半成品、哪些在等设计/等客户/等你拍板。
3. **下一步该做什么**：按"HR 感觉得到的程度"排序，说清为什么先做这个、不先做那个。

把这三条用**人话**讲回给我。讲不清楚，说明你还没读懂——回去读 §8 的 1、2、3。
然后才是：核现场（git/库有没有异常）→ 挑一件最该做的派下去 → 验收。
